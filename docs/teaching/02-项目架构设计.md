# 02 - 项目架构设计

## 一、分层架构

项目按 `infra-dev-scaffolding` 的习惯组织：平台能力在 `internal/platform`，业务能力按领域拆到 `internal/customer`、`internal/knowledge`、`internal/ops`，前端控制台放在 `apps/console`。

```text
┌─────────────────────────────────────────────┐
│ apps/console                                │
│ React + TypeScript + Vite                   │
├─────────────────────────────────────────────┤
│ cmd/platform-all                            │
│ Go net/http + ServeMux                      │
├─────────────────────────────────────────────┤
│ internal/customer                           │
│ 多轮会话、消息发送、转人工触发              │
├─────────────────────────────────────────────┤
│ internal/knowledge                          │
│ 知识文章、检索、知识缺口处理                │
├─────────────────────────────────────────────┤
│ internal/ops                                │
│ 运营指标、规则测试、工单处理                │
├─────────────────────────────────────────────┤
│ internal/platform                           │
│ config / httpjson / service / store / db    │
├─────────────────────────────────────────────┤
│ PostgreSQL + pgx + SQL                      │
└─────────────────────────────────────────────┘
```

## 二、请求流程

### 前端请求流程

```text
用户操作
  -> apps/console/src/App.tsx
  -> fetch('/api/...') typed helpers
  -> Vite proxy
  -> Go HTTP API
```

### 后端请求流程

```text
HTTP request
  -> ServeMux route
  -> httpjson decode / validation
  -> platform service
  -> Runtime store interface
  -> memory store or PostgreSQL store
  -> httpjson response envelope
```

后端保持显式、少魔法：

- 路由在命令入口和业务 handler 中清晰挂载。
- API 返回统一 envelope。
- 存储通过 `Runtime` 接口隔离。
- PostgreSQL 使用 SQL migration，不依赖自动建表。

## 三、核心领域模型

### Conversation

表示一段客服会话，包含用户、渠道、状态、最近消息、最后策略和证据。

关键字段：

| 字段 | 说明 |
|------|------|
| `id` | 会话 ID |
| `customer_name` | 客户名称 |
| `channel` | 来源渠道 |
| `status` | active、transferred、closed |
| `messages` | 多轮消息 |
| `last_policy` | 最近一次策略，例如 `rag+rule`、`fallback`、`transfer` |

### Message

表示用户或 Agent 的一条消息。

| 字段 | 说明 |
|------|------|
| `role` | user 或 assistant |
| `content` | 消息内容 |
| `evidence` | 本轮引用的知识证据 |
| `confidence` | 回复置信度 |

### KnowledgeArticle

表示可被检索的客服知识。

| 字段 | 说明 |
|------|------|
| `title` | 知识标题 |
| `body` | 知识正文 |
| `tags` | 检索标签 |
| `status` | draft 或 published |

### KnowledgeGap

表示系统没有足够证据回答的问题。

| 字段 | 说明 |
|------|------|
| `question` | 用户原始问题 |
| `status` | open、resolved、article_created |
| `conversation_id` | 来源会话 |

### TransferTicket

表示需要人工介入的客服工单。

| 字段 | 说明 |
|------|------|
| `reason` | 转人工原因 |
| `status` | open、resolved |
| `conversation_id` | 来源会话 |

## 四、模块边界

### `internal/customer`

负责用户会话链路：

- 列出会话
- 创建会话
- 发送消息
- 组织多轮上下文
- 触发知识检索
- 根据证据和规则决定回复策略
- 创建转人工工单

它不直接关心数据库细节，只依赖 `Runtime`。

### `internal/knowledge`

负责知识运营链路：

- 列出知识文章
- 关键词检索知识
- 记录知识缺口
- 关闭知识缺口
- 从知识缺口创建文章

它提供“Agent 能不能回答”的事实基础。

### `internal/ops`

负责运营可观测与人工动作：

- 聚合 dashboard 指标
- 测试规则命中结果
- 关闭转人工工单

它不承担核心对话生成，而是让系统可运营、可教学、可排查。

### `internal/platform`

负责脚手架继承能力：

- `config`：环境变量配置
- `httpjson`：统一 JSON envelope
- `service`：业务服务组装
- `store`：内存实现与 PostgreSQL 实现
- `db`：数据库连接和 migration

## 六、数据模型初稿

当前 PostgreSQL migration 建立以下核心表：

| 表 | 说明 |
|----|------|
| `conversations` | 客服会话 |
| `messages` | 多轮消息 |
| `knowledge_articles` | 知识文章 |
| `knowledge_gaps` | 知识缺口 |
| `transfer_tickets` | 转人工工单 |

设计原则：

- 对话历史必须可追踪。
- 知识证据必须可回看。
- 没证据时不能强答。
- 运营动作要落表，而不是只存在于日志。

## 七、关键设计决策

### 决策 1：为什么使用 Go 标准库 HTTP

教学项目要突出业务边界和工程习惯。标准库 HTTP 足够表达路由、handler、JSON、错误处理，也更容易让学生看清每一层做了什么。

### 决策 2：为什么不用 ORM

客服 Agent 的数据模型不复杂，但“哪些数据被记录、哪些字段是边界”很重要。SQL migration 能让表结构成为清晰的教学材料，也与脚手架习惯一致。

### 决策 3：为什么保留内存存储

内存存储用于快速演示和单元测试，PostgreSQL 存储用于真实持久化。两者实现同一个 `Runtime` 接口，方便教学“接口隔离”和“运行时替换”。

### 决策 4：为什么把知识缺口作为一等模型

可靠 Agent 的重点不是永远回答，而是知道什么时候不能回答。知识缺口让系统从“不知道”进入运营闭环，这是防幻觉的关键产品设计。

## 八、目录结构

```text
apps/
  console/                 React 控制台
cmd/
  platform-all/            本地一体化服务
  customer-service-api/    客服 API 入口
  ops-api/                 运营 API 入口
  console-web/             控制台静态入口
  migrate-db/              数据库迁移入口
internal/
  customer/                会话与消息 API
  knowledge/               知识与缺口 API
  ops/                     指标、规则、工单 API
  platform/
    config/                环境变量配置
    db/                    PostgreSQL 连接与迁移
    httpjson/              统一响应
    service/               服务组装
    store/                 Runtime 接口与实现
infra/
  postgres/migrations/     SQL migration
  local/                   本地 docker compose
scripts/                   脚手架校验脚本
contracts/                 API 与平台约束
project_document/          项目设计文档
```
