# 智能电商客服系统 —— 面试叙事导航图

> 这份导航图是你面试的"作战地图"。遇到任何问题，在脑子里定位到树上的节点，顺着路线往下讲就行。
>
> 阅读建议：先花 40 分钟通读一遍，再花 40 分钟把深潜知识点的比喻用自己的话说一遍，最后 40 分钟对着镜子走一遍主线路径。

# 第一份：【复试面试版】—— 打动导师的心

> 目标听众：研究生导师
> 导师在看什么：好奇心、研究深度、学术探究精神、动手能力
> 核心策略：让导师觉得"这个学生不是在背项目，是在思考问题"

---

## 一、开场锚点（30 秒定生死）

> 面试开场最重要的不是"介绍项目"，是"让老师想继续听"。你只有 30 秒，一句话要勾住他的兴趣。

### 风格 A：痛点驱动型（推荐大多数人用）

> "我做了一个智能电商客服系统。起因很简单——我网购时经常被客服机器人的固定话术逼疯，它只会回'请稍等'，但什么问题都解决不了。我就想，如果把大模型接进来，让它真的'理解'我在问什么，再从真实的商品和活动数据里找到答案来回复，效果会怎样？所以我做了这个系统，而且特别关注了一个问题：大模型 API 不稳定的时候，系统怎么还能正常服务。"

⭐ 为什么用这个开场：老师一听就知道你有真实的问题意识，不是"为了做项目而做项目"。最后那句"大模型不稳定怎么办"埋了个钩子，老师大概率会追问。

### 风格 B：技术好奇型（适合本身对 AI 有兴趣的同学）

> "我对大模型应用很感兴趣，特别好奇一个问题：大模型虽然什么都能聊，但它的回答经常'一本正经地胡说八道'——学术上叫幻觉问题。我想试试，能不能在一个真实的电商客服场景里，用知识库检索来'约束'大模型，让它基于真实数据回答而不是瞎编。做完之后我还发现了另一个有意思的问题：LLM API 随时可能挂，所以我设计了一个双引擎降级机制。"

⭐ 为什么用这个开场：直接抛"幻觉问题"这个学术关键词，老师会觉得你有阅读和思考。

### 风格 C：对比思考型（适合思维清晰、表达能力强的同学）

> "我做了一个智能客服系统，但和市面上大多数'玩具级别'的 ChatBot 不一样——那些 Demo 通常就是套个 API 聊聊天，没有知识约束、没有降级方案、不能多轮对话。我做的是一个接近生产环境的系统：10 张数据库表、54 个 API 接口、8 步对话流水线、双引擎降级，还有推理过程可视化。我想探索的是，怎么把大模型从一个'聊天玩具'变成一个'真正能用的工程系统'。"

⭐ 为什么用这个开场：直接跟"玩具项目"划清界限，用具体数字（10 张表、54 个接口、8 步流水线）建立信任感。

## 二、主线路径（树状结构）

> 下面是三条主线，像高速公路的三个匝道——起点不同，但都能开到"终点"（展现你的能力）。
> 根据面试官的提问选择匝道入口，进去之后沿节点顺序讲就行。

### 路线 A：从"解决了什么真实问题"出发

> 适合回答："介绍一下你的项目" / "这个项目做什么的"

```
问题切入
  "电商每天大量重复咨询，传统方案要么纯人工太贵，要么硬编码规则体验差"
  │
  ├─ 节点1：我的方案 ──────────────────────────────────────────────
  │   说什么："我把大模型和知识库结合，让AI基于真实数据回答问题"
  │   老师心理：这个思路清晰，知道 LLM 不能裸用
  │
  ├─ 节点2：双引擎设计 ────────────────────────────────────────────
  │   说什么："但大模型 API 随时可能挂，所以我做了双引擎——LLM 挂了自动切关键词规则引擎"
  │   老师心理：这个学生有工程意识，知道系统要可靠
  │
  ├─ 节点3：8步对话流水线 ─────────────────────────────────────────
  │   说什么："一条消息进来要走 8 步：保存→分析意图→检索知识→生成回复→..., 像工厂流水线"
  │   老师心理：看得出做得比较深入，不是随便套了个API
  │
  ├─ 节点4：推理可视化 ────────────────────────────────────────────
  │   说什么："每次对话的推理过程都透明展示，用户能看到 AI 是怎么思考的"
  │   老师心理：有可解释性意识，这在 AI 研究中很重要
  │
  └─ 节点5：预留的扩展方向 ────────────────────────────────────────
      说什么："知识表预留了 vectorized 字段，为后续接入向量数据库做语义检索做准备"
      老师心理：有技术规划能力，不只是做了当下的功能
```

### 路线 B：从"双引擎降级设计"出发

> 适合回答："你觉得这个项目最有挑战的部分是什么" / "说说你遇到的难点"

```
一个真实故事切入
  "有次调试的时候，LLM API 突然超时了，页面直接卡死。我就想，如果这是线上呢？"
  │
  ├─ 节点1：问题的严重性 ──────────────────────────────────────────
  │   说什么："大模型 API 有三个不稳定因素：网络超时、限流、Key过期。任何一个都会让用户等半天"
  │   老师心理：有问题分析的习惯，不是遇到问题就绕开
  │
  ├─ 节点2：降级方案设计 ──────────────────────────────────────────
  │   说什么："我设计了两个降级点：分析阶段LLM挂了走关键词识别，回复阶段LLM挂了走模板拼接"
  │   老师心理：方案有层次，不是一个简单的 if-else
  │
  ├─ 节点3：技术实现 ──────────────────────────────────────────────
  │   说什么："所有 LLM 调用都 catch 异常返回 null，调用方通过 null 判断走哪个引擎"
  │   老师心理：代码层面考虑得很细
  │
  ├─ 节点4：可观测性 ──────────────────────────────────────────────
  │   说什么："日志里标注了分析引擎=LLM还是关键词，回复引擎=LLM还是规则，方便排查"
  │   老师心理：有运维意识，知道线上系统需要可观测
  │
  └─ 节点5：引申思考 ──────────────────────────────────────────────
      说什么："这让我意识到，做AI应用和做传统应用最大的区别就是'不确定性管理'"
      老师心理：能从具体问题抽象出一般性认知，有研究潜力
```

### 路线 C：从"AI + 传统工程的融合"出发

> 适合回答："你对大模型/AI有什么看法" / "为什么选这个方向"

```
观察切入
  "我发现很多大模型应用 Demo 都是玩具级别的——套个 API，聊聊天，没有数据支撑，没有降级"
  │
  ├─ 节点1：AI 裸用的问题 ─────────────────────────────────────────
  │   说什么："大模型最大的问题是幻觉——它会一本正经地编造信息。客服场景下这是致命的"
  │   老师心理：对 AI 局限性有认识，不是盲目追捧
  │
  ├─ 节点2：知识约束的思路 ────────────────────────────────────────
  │   说什么："所以我用知识检索来约束——先从数据库找到真实的商品、活动数据，注入提示词让 AI 基于事实回答"
  │   老师心理：了解 RAG 的基本思想
  │
  ├─ 节点3：工程化的考量 ──────────────────────────────────────────
  │   说什么："但光有 AI 不够，还需要事务管理、异常处理、分层架构、连接池这些传统工程能力"
  │   老师心理：技术视野比较全面
  │
  ├─ 节点4：两种温度的选择 ────────────────────────────────────────
  │   说什么："分析意图用 temperature 0.1 要确定性，生成回复用 0.7 要创造性——同一个模型不同任务参数不同"
  │   老师心理：对模型参数有理解，不是黑盒调用
  │
  └─ 节点5：从这个项目学到什么 ────────────────────────────────────
      说什么："AI 应用的本质是'用确定性工程包裹不确定性模型'——这也是我想继续深入研究的方向"
      老师心理：有提炼、有方向感，适合做研究
```

## 三、深潜知识点

> 下面每个知识点都有四个部分：通俗比喻（让不懂的人秒懂）→ 技术本质（准确描述原理）→ 我的理解（你个人的思考）→ 可能追问（老师最可能问什么 + 怎么答）
>
> ⭐ 面试的时候，先说比喻让老师觉得你会沟通，再说技术本质让老师觉得你真懂，最后说你的理解让老师觉得你有想法。

### 深潜 1：意图识别（LLM vs 规则引擎）

🎯 **通俗比喻**：
> 想象你开了一家餐厅，门口站了两个迎宾。第一个是一个特别聪明但偶尔迟到的人（LLM），他一看客人的表情和穿着就知道"这位想吃商务套餐"。第二个是一个很靠谱但比较死板的人（规则引擎），他只会看客人手里拿的菜单牌——牌上写"商务"就带去商务区。正常情况聪明迎宾上班就用他，他迟到了就让靠谱迎宾顶上，客人不能在门口站着。

📖 **技术本质**：
意图识别就是搞清楚用户这句话"想干什么"。LLM 路径是把用户消息连同 Prompt 发给大模型，要求返回结构化 JSON（场景、意图编码、置信度、情绪），temperature 设 0.1 保证确定性。规则路径是用 `containsAny()` 方法做关键词匹配——消息里包含"优惠、打折、促销"就判定为"商品优惠查询"意图，覆盖了 5 种核心意图和 30+ 情绪关键词。

💭 **我的理解**：
"我一开始觉得有了大模型还要什么关键词匹配，后来 API 超时了一次我就想明白了——生产系统不能有单点故障。而且关键词匹配虽然笨，但它快、稳定、不花钱。这其实就是工程里常说的'优雅降级'——能用好的就用好的，好的不行就用能用的。"

❓ **可能追问**：
- **"LLM 做意图识别和传统的分类模型（比如 BERT）比有什么优劣？"**
  → "LLM 的优势是零标注数据、理解能力强，写个 Prompt 就能用；劣势是延迟高、成本高、输出不完全可控。BERT 分类器准确率更高更稳定，但需要大量标注数据去训练。如果真正上生产，可能会用 BERT 做主力、LLM 做兜底，跟我现在正好反过来。"
- **"你的关键词列表怎么确定的？覆盖率够吗？"**
  → "是根据电商客服最常见的 5 类场景手动梳理的，目前覆盖了售前、售后、物流、支付和通用咨询。覆盖率肯定不完美，没匹配上的统一归为'通用咨询'。如果要提升，可以从真实对话日志里统计高频词动态补充，或者直接改成从数据库表加载——这个表我已经建好了，就是 `cs_scene_intent`。"

---

### 深潜 2：双引擎降级 / 容错设计

🎯 **通俗比喻**：
> 就像高速公路和国道的关系。正常情况走高速（LLM），又快体验又好。但高速可能封路（API 超时）、可能限行（限流）、可能收费站坏了（Key 过期）。这时候导航自动切到国道（规则引擎），虽然慢点、景色差点，但目的地一样能到。关键是——切换的过程对乘客（用户）是无感的，他只知道自己到了。

📖 **技术本质**：
系统有两个降级切换点。分析阶段：`LlmService.analyzeUserInput()` 调 LLM 失败返回 null，`ChatService` 自动切换到三个 fallback 方法（场景识别、意图分析、情绪分析各一个），用关键词匹配输出结果。回复阶段：`LlmService.generateReply()` 失败返回 null，自动切换到规则引擎 `generateReply()`，基于意图和知识用模板拼接回复。所有 LLM 调用都套了 try-catch，任何异常都吞掉返回 null，让降级逻辑由调用方控制。

💭 **我的理解**：
"双引擎的核心不是'两套代码'，而是'一个承诺'——不管后面怎么出错，用户永远能得到一个回复。我在设计的时候想到了一句话：'最好的容错设计是用户感知不到容错在发生'。日志里会标注用的是哪个引擎，但用户界面上看不出区别。"

❓ **可能追问**：
- **"降级后回复质量差了怎么办？用户能接受吗？"**
  → "确实会差一些，但有总比没有好。实际上规则引擎回复的是经过整理的标准话术，虽然不如 LLM 灵活，但信息准确度反而更高。而且我觉得可以加一个'引擎标识'——降级模式下自动追加一句'如需进一步帮助请联系人工客服'，把期望管理好。"
- **"除了返回 null 这种方式，还有什么降级策略？"**
  → "还可以用超时降级——设一个 3 秒的超时阈值，超了就切换，不用等到真正报错。也可以用熔断器模式，比如连续 5 次失败就直接跳过 LLM 一段时间，不再尝试，减少无谓等待。Spring Cloud 里有 Resilience4j 可以做这个。"

### 深潜 3：知识检索（关键词匹配 vs 语义检索）

🎯 **通俗比喻**：
> 你去图书馆找书。关键词匹配就像翻卡片目录——你要找"运动鞋"，它就在卡片里一张张翻有没有"运动鞋"这三个字。语义检索就像问一个读过全馆书的图书管理员——你说"我想跑步穿的舒服的鞋"，他虽然你没说"运动鞋"，但他懂你的意思。我的项目目前用的是翻卡片的方式，但我在每张卡片上预留了一个"管理员读书笔记"的位置（vectorized 字段），以后可以升级。

📖 **技术本质**：
当前知识检索采用关键词子串匹配算法 `calculateMatchScore()`：先做单字符命中统计，再做 2-6 字符的连续子串匹配（连续子串权重更高，因为"运动鞋"连续命中比"运"和"鞋"分别命中更有意义），最后归一化到 [0,1]，阈值 0.3 以上才算命中，取 Top 3 返回。检索优先级：前端手动选择（score=0.99）> 自动关键词匹配商品 > 自动匹配活动 > FAQ 匹配。

💭 **我的理解**：
"有人可能觉得关键词匹配太简单了，但我是有意识地做这个选择的。因为项目的核心目标是展示'大模型+知识库'的架构思路，知识检索只是其中一环。如果一开始就上向量数据库，光 Embedding、Milvus 部署、向量索引就要花一两周，反而模糊了重点。先用简单的方案跑通全链路，再逐步升级——这其实是软件开发里'先让它 work，再让它 work better'的原则。"

❓ **可能追问**：
- **"关键词匹配有什么缺陷？举个例子？"**
  → "最大的缺陷是不理解语义。比如用户问'有没有适合送女朋友的礼物'，关键词匹配不到任何商品名，但实际上可能'香水''丝巾'都是好推荐。语义检索就能理解'送女朋友'和'礼品类商品'之间的语义关联。"
- **"如果要升级成语义检索，你会怎么做？"**
  → "三步：第一，用 Embedding 模型（比如 text-embedding-3-small）把知识库里的商品描述转成向量，存到向量数据库（Milvus 或 Pinecone）；第二，用户发消息时也转成向量，做余弦相似度匹配；第三，把匹配结果同样注入 LLM 提示词。数据库里的 vectorized 字段就是为这个预留的。"

### 深潜 4：多轮对话与上下文管理

🎯 **通俗比喻**：
> 想象你打电话给客服，第一个问题问"你们有什么运动鞋？"，第二个问题问"那它多少钱？"。如果每次都是不同的客服接（单轮对话），第二个客服根本不知道"它"是什么。多轮对话就是让同一个客服一直在线（上下文），他记得你之前问了什么。但这个客服的记忆力有限——我设置了最多记最近 10 条消息，太早的就忘了，不然他脑子会装不下（Token 超限）。

📖 **技术本质**：
多轮上下文通过数据库 + LLM messages 数组实现。每条消息存入 `cs_chat_message` 表，带 sessionId 做会话隔离。生成回复前，从数据库取同 session 最近 10 条历史消息（排除本轮刚保存的），按时间正序排列，注入到 LLM 的 messages 数组中，格式为 `[system 提示词, ...历史消息, 当前 user 消息]`，这是 OpenAI Chat Completions API 的标准多轮格式。

💭 **我的理解**：
"多轮对话看起来简单——把历史消息传进去就行——但实际有很多要权衡的。传多少条？传多了 Token 费用高、延迟大；传少了上下文不够 AI 理解不了。我选了 10 条，是考虑到客服场景一般一个问题聊几轮就解决了，10 条足够覆盖一个完整的咨询流程。而且我用数据库存历史消息而不是内存，这样用户关掉页面再打开，历史记录还在。"

❓ **可能追问**：
- **"10 条够不够？怎么确定这个数字的？"**
  → "这是一个经验值。电商客服通常一个问题 3-5 轮对话就解决了，10 条能覆盖 2-3 个连续话题。如果要更科学，可以统计真实对话数据的轮次分布来决定。另外也可以做动态窗口——对话轮次少时全部传入，超过阈值时做摘要压缩。"
- **"指代消解怎么处理的？比如用户说'它多少钱'，'它'指什么？"**
  → "目前靠 LLM 自身的理解能力——因为历史消息里有上下文，LLM 大部分情况能推断出'它'指的是前面提到的商品。但这不完美，复杂场景下可能出错。更好的方案是加一个显式的实体追踪模块，记住当前对话的核心实体（比如'运动鞋 Pro'），在后续轮次自动关联。"

### 深潜 5：Prompt Engineering（系统提示词设计）

🎯 **通俗比喻**：
> 你招了一个超级聪明的实习生（大模型），但他刚来什么都不了解。你给他写了一份"岗位说明书"（System Prompt），上面写着：你的角色是客服、你要怎么说话、什么能说什么不能说。然后每次有客户来，你还会给他一张"速查小纸条"（增强提示词），上面写着：这个客户在问优惠、他的心情不太好、这是相关的商品信息……有了岗位说明书 + 速查小纸条，这个实习生就能给出靠谱的回答了。

📖 **技术本质**：
系统提示词分两层。基础层是 `SYSTEM_PROMPT` 常量，定义角色设定和 6 条行为规则（比如"基于知识回答，不编造"）。增强层是 `buildEnhancedPrompt()` 方法动态拼接的上下文信息：当前场景类型、用户意图、用户情绪（负面情绪追加安抚指令）、检索到的知识（商品/活动/FAQ）。两次 LLM 调用的 Prompt 完全不同：分析用的 Prompt 要求输出结构化 JSON，生成回复用的 Prompt 要求输出自然语言。

💭 **我的理解**：
"Prompt 工程看起来就是在'写作文'，但其实它更像'写合同'——你要把每个条款写清楚，不然对方（模型）会按自己的理解来。比如我在分析 Prompt 里写了'返回纯 JSON'，但有些模型还是会在外面包一层 markdown 代码块，所以代码里还要额外处理这种情况。好的 Prompt 不只是'写出来'，还要经过反复测试调整。"

❓ **可能追问**：
- **"你的提示词是怎么迭代的？改了几版？"**
  → "最初版只有角色设定，LLM 回复经常跑题或者编造信息。然后我加了'基于提供的知识回答'这条约束，减少了幻觉。再后来发现用户情绪负面时回复太冷淡，就加了情绪判断和安抚指令。最终版是 6 条规则 + 动态上下文注入，大概迭代了 4-5 个版本。"
- **"Few-shot 和 Zero-shot 的区别？你用的哪种？"**
  → "Zero-shot 是直接告诉模型'做什么'，不给示例；Few-shot 是在 Prompt 里给几个输入-输出的示例让模型学着做。我目前用的是 Zero-shot，因为分析任务相对简单，模型能理解。如果意图更复杂，可以改成 Few-shot——在 Prompt 里加 2-3 个'用户问→JSON 输出'的示例，提高输出的格式稳定性。"

### 深潜 6：LLM 幻觉问题与知识约束

🎯 **通俗比喻**：
> 大模型就像一个记忆力超强但有时候分不清"记住的"和"脑补的"的人。你问他"这双鞋打几折"，他可能自信地说"打七折"——但其实根本没有这个折扣，是他自己编的。解决办法就是给他一张"cheat sheet"（小抄）——你把真实的折扣信息写在纸上递给他，告诉他"只能按纸上的信息回答"。这就是我项目里"知识检索 + 注入提示词"在做的事。

📖 **技术本质**：
幻觉（Hallucination）是大模型生成看似合理但事实不正确内容的现象。项目通过 RAG（Retrieval-Augmented Generation，检索增强生成）的简化版来缓解：先从数据库检索真实的商品、活动、FAQ 数据，通过 `buildKnowledgeText()` 格式化为结构化文本，注入到系统提示词的"参考知识"部分，并在规则中明确要求"基于提供的知识信息回答，禁止编造不存在的商品和活动"。

💭 **我的理解**：
"幻觉问题本质上是因为 LLM 是概率模型——它不是在'查询事实'，而是在'预测最可能的下一个词'。所以它生成的内容语法流畅、逻辑通顺，但不一定为真。知识注入相当于给概率分布加了一个'先验约束'——当提示词里已经有了真实数据，模型大概率会基于这些数据回答，而不是自己编。但这不是 100% 有效的，极端情况下模型还是可能无视约束。"

❓ **可能追问**：
- **"除了知识注入，还有什么方法减少幻觉？"**
  → "几个方向：一是降低 temperature，让输出更确定性；二是加后处理校验——生成回复后检查里面提到的商品名、价格是否真实存在；三是用 RLHF（人类反馈强化学习）微调模型让它更守规矩，但这超出了项目范围。"
- **"你怎么验证你的知识约束是有效的？"**
  → "两种方式：一是对比测试——同一个问题，有知识注入和没有知识注入的回复对比，看是否基于真实数据；二是通过推理过程可视化——前端展示了知识检索命中了哪些数据，人工可以核实回复是否与命中数据一致。"

### 深潜 7：Temperature 参数在不同场景的选择

🎯 **通俗比喻**：
> Temperature 就像创作的"自由度旋钮"。调到最低（0-0.2），大模型就像一个严谨的会计——让他算 1+1，永远是 2，不会创新也不会出错。调到中间（0.5-0.8），像一个文案写手——同一个主题能写出不同版本，既有创意又不太离谱。调到最高（1.5+），像一个喝了酒的诗人——可能蹦出天才灵感，也可能胡言乱语。

📖 **技术本质**：
Temperature 控制的是 softmax 函数的输出概率分布。值越低，概率集中在最高概率的 token 上，输出越确定；值越高，概率越分散，低概率 token 也有机会被选中，输出越随机。项目中两次 LLM 调用使用不同温度：`analyzeUserInput()` 用 0.1（需要稳定的 JSON 结构化输出），`generateReply()` 用 0.7（需要自然多样的客服回复）。

💭 **我的理解**：
"我觉得 temperature 的选择本质上是在'准确性'和'多样性'之间做权衡。意图分析就像做选择题，答案应该是确定的，所以用低温度。生成回复就像写作文，同一个意思可以有多种表达方式，用适中的温度让回复不那么机械。这个参数没有'最佳值'，取决于场景需求，要通过实际测试来调。"

❓ **可能追问**：
- **"temperature 0 和 0.1 有什么区别？"**
  → "temperature 0 理论上每次输出完全一样，但 OpenAI 官方文档说由于浮点运算等原因实际不保证完全确定性。0.1 基本也是高度确定的，但给了极小的随机空间。实际效果差别很小，我选 0.1 是留一点点灵活性。"
- **"如果用户情绪是负面的，temperature 要不要调整？"**
  → "这是个有意思的想法。负面情绪的场景需要更谨慎的回复，理论上可以把 temperature 调低一些（比如 0.4-0.5），减少'说错话'的风险。目前我没做这个动态调整，但这确实是一个有价值的优化方向。"

### 深潜 8：对话系统的评估方法

🎯 **通俗比喻**：
> 评估一个客服好不好，就像评一家餐厅。不能只看"有没有上菜"（系统有没有回复），还要看"菜品对不对"（回答是否准确）、"上菜快不快"（响应延迟）、"服务态度好不好"（语气是否友好）、"有没有推荐对的菜"（意图是否识别正确）。而且最重要的是，客人吃完会不会再来（用户满意度）。

📖 **技术本质**：
对话系统的评估一般分几个维度：意图识别准确率（识别对了没）、知识检索召回率和精确率（找对了没、找全了没）、回复的相关性和流畅性（回答得好不好）、响应延迟（快不快）、用户满意度（用户评分）。项目中通过日志链路记录了每次对话的分析引擎类型、意图识别结果、知识检索命中数和匹配分数、回复引擎类型等指标。前端的推理过程可视化也支持人工审查。

💭 **我的理解**：
"说实话，评估是 AI 对话系统最难的部分之一。传统软件的测试有'标准答案'——输入 A 应该输出 B。但 AI 客服的回复没有唯一的标准答案，'不错的推荐'和'很好的推荐'可能都算对。所以除了自动化指标，人工评估也必不可少。我项目里的推理过程可视化，其实就是为人工审查提供了便利——评估者可以看到 AI 每一步的决策过程，判断'这步做对了没'，而不只是看最终回复。"

❓ **可能追问**：
- **"如果让你设计一个评测方案，你会怎么做？"**
  → "我会分三层。第一层自动化：准备 100 条标注好意图的测试用例，跑意图识别准确率。第二层半自动化：让系统回答这 100 条问题，人工打 1-5 分评估回复质量。第三层用户调研：上线后收集用户对每次对话的评分和反馈。还可以做 A/B 测试——一组用 LLM，一组用规则引擎，对比满意度。"
- **"你有跑过什么评测吗？"**
  → "系统层面我测试了双引擎降级——手动关闭 LLM 开关，验证系统能否正常走规则引擎回复。也测试了不同类型问题（优惠、退货、物流）的意图识别准确率，目前在预设的测试集上表现不错。但系统化的大规模评测还没做，这是后续可以完善的方向。"

### 高频陷阱题应对

**陷阱 1："你这个和市面上的客服机器人有什么区别？"**

> ⭐ 千万别慌，也别贬低自己。关键是定位差异化。

"市面上的客服机器人大多分两种：一种是纯规则的，智能程度有限；一种是直接套 LLM API 的 Demo，没有知识约束容易幻觉，也没有降级方案。我的项目想探索的是'两者结合'——LLM 提供语义理解能力，知识库提供事实约束，规则引擎提供可靠性兜底。而且我特别注重了可观测性——推理过程完全可视化，每一步都标注了用的哪个引擎。当然这不是一个商用级产品，更多是在探索这种'大模型+传统工程'的融合架构怎么设计。"

**陷阱 2："知识检索用关键词匹配是不是太简单了？"**

> ⭐ 把"简单"变成"有意识的技术选择"。

"这是一个有意识的设计决策。项目的核心目标是展示'大模型+知识库'的架构思路——从意图识别到知识检索到回复生成的完整链路。如果一开始就上向量数据库，光 Embedding 模型选型、Milvus 部署、索引调优就是一个大工程，反而会模糊重点。所以我先用简单的关键词匹配跑通全链路，同时在每张知识表上预留了 vectorized 字段，为后续升级成语义检索做好了准备。这其实是工程中'先让它 work，再让它 work better'的原则。"

**陷阱 3："被问到不会的知识点怎么办？"**

> ⭐ 三步法：承认 → 展示你知道的 → 给出学习方向

模板："这个细节我还没有深入研究过，不过我了解到 [相关的基础知识]，如果要在我的项目里实现的话，我初步的想法是 [你的推测]，具体的话需要进一步调研 [哪方面的资料]。"

举例——被问到"RLHF 是什么？你了解吗？"

"RLHF 我了解基本概念——它是用人类反馈来微调模型的行为，让模型的输出更符合人的期望。但具体的训练流程和奖励模型设计我还没有深入研究。在我的项目里，我用的是更轻量的方式来控制 LLM 行为——通过精心设计的 System Prompt 和知识注入来约束输出。如果要更进一步，RLHF 或者 DPO（Direct Preference Optimization）是值得深入研究的方向。"

## 五、故事线自洽包

> ⭐ 下面这些"背景故事"要提前想好，面试时像聊天一样自然地说出来。

### 为什么选客服方向？

"其实起因挺朴素的。我自己网购比较多，经常遇到客服机器人只会回固定话术的情况——你问一句'有什么优惠'，它回你一大段不相关的模板。后来 ChatGPT 出来之后，我就想试试，能不能做一个真正'懂'客户问题的客服。电商客服场景还有个好处——需求明确、知识边界清晰（就是那些商品和活动数据），特别适合练手大模型应用。"

### 做的过程中遇到过什么真实挑战？

**挑战 1：8 步流水线的设计**
"一开始我想的是'接到消息 → 调 LLM → 返回回复'，三步完事。但做着做着发现不行——LLM 回复质量取决于你给它什么信息。所以我加了意图分析、知识检索、上下文构建这些步骤。最终变成了 8 步，每一步的输出是下一步的输入，像流水线一样串起来。"

**挑战 2：LLM 返回 JSON 的不确定性**
"让 LLM 返回结构化 JSON 比想象中难。有时候它会在 JSON 外面包一层 markdown 代码块，有时候字段名大小写不一致，偶尔还会返回多余的解释文字。我在代码里写了好几层解析逻辑——先去掉 markdown 包裹，再做 JSON parse，parse 失败就返回 null 走兜底。"

**挑战 3：关键词匹配算法的调优**
"最初用的是简单的 `contains()` 判断，但发现太粗糙了——用户输入'运动鞋推荐'会匹配到所有包含'运'字的商品。后来改成了连续子串匹配 + 加权的方式，连续匹配'运动鞋'三个字的得分远高于只匹配到一个'运'字的。还加了 0.3 的阈值过滤低相关结果。"

### "双引擎"这个设计是怎么想到的？

"有次在本地调试的时候，LLM API 突然超时了，大概等了 10 秒页面才报错。我当时就想——如果这是上线了的系统呢？用户等 10 秒看到报错，体验直接崩了。然后我想到了我以前看过的一个概念叫'优雅降级'——核心服务挂了要有备选方案。LLM 的备选方案是什么？就是传统的关键词规则引擎。虽然没有 LLM 那么智能，但起码能给用户一个有用的回复。所以我就设计了双引擎——LLM 是主引擎、规则是备引擎，切换过程对用户无感。"

### 被问"这代码是你写的吗"？

"是我独立开发的。当然开发过程中我会参考技术文档和开源项目的实现思路，也会用 AI 工具帮我查文档和排 Bug。但架构设计——比如为什么做双引擎、为什么用 8 步流水线、知识检索的优先级怎么定——这些是我自己思考的。代码里每个设计决策我都能讲清楚为什么这么做。"

### 未来想法（关联读研方向）

"做这个项目让我对对话系统特别感兴趣。一方面是技术层面——怎么让 AI 更准确地理解用户意图、怎么减少幻觉、怎么在多轮对话中维持上下文；另一方面是工程层面——大模型应用和传统软件工程的结合还有很多课题没有被充分研究。如果有机会读研，我希望能在自然语言处理或者对话系统方向继续深入，特别是知识增强的对话生成、对话系统的可控性和评估方法这几个课题。"

## 一、开场锚点（30 秒定生死）

### 风格 A：系统定位型（推荐大多数人用）

> "我做了一个智能电商客服系统，前后端分离架构——后端 Spring Boot 3.4，前端 Vue 3，对接 LLM 大模型。整体规模是 10 张数据库表、54 个 RESTful API 接口、8 步对话处理流水线。核心亮点是双引擎降级设计——LLM 可用时走大模型生成回复，LLM 不可用时自动切到关键词规则引擎，保证系统 0 停服。"

⭐ 为什么用这个开场：开门见山说技术栈和规模，用数字建立"这不是一个玩具项目"的认知。最后的"0 停服"是工程类面试官最关心的。

### 风格 B：业务价值型（适合偏业务的团队）

### 深潜 9：Spring Boot 分层架构

🎯 **通俗比喻**：
> 就像一家公司的组织架构。Controller 是前台接待——接电话（HTTP 请求）、记下客户要求、转给对应部门。Service 是业务部门——真正干活的。Repository 是档案室——存取数据。Config 是行政部——配置公司的各种规章制度（跨域、连接池、日志）。大家各干各的，前台不需要知道档案室怎么管文件的。

📖 **技术本质**：
项目采用标准的 Spring Boot 三层架构。Controller 层（3 个）负责接收请求、参数校验、调用 Service、返回统一响应 `R<T>`。Service 层（4 个）负责核心业务逻辑，ChatService 包含 8 步对话流水线，LlmService 封装 LLM 调用。Repository 层（10 个）继承 JPA 的 `JpaRepository`，提供标准 CRUD。横切关注点通过 AOP 切面处理：`ControllerLogAspect` 记录请求日志，`FacadeAspect` 统一参数校验和异常处理，`SqlLogAspect` 记录 SQL 执行情况。

💭 **我的理解**：
"分层的核心好处是解耦。比如我要把知识检索从关键词匹配换成向量检索，只需要改 Service 层的实现，Controller 和 Repository 完全不用动。AOP 切面的好处也是一样——我想加一个请求耗时统计，不需要在每个 Controller 方法里写，加个切面统一处理就行。"

❓ **可能追问**：
- **"为什么用 AOP 做日志而不是在方法里直接打 log？"**
  → "两个原因：一是不侵入业务代码，Service 方法只关注业务逻辑；二是统一管理，所有 Controller 的请求日志格式一致，修改格式只改一处。这就是 AOP 的核心价值——横切关注点集中管理。"
- **"@Facade 注解是干什么的？"**
  → "是我自定义的组合注解，相当于把参数校验和异常处理绑在一起。方法加了 @Facade，进来时自动校验参数，出异常时自动包装成统一响应格式。减少了每个 Controller 方法里的模板代码。"

### 深潜 10：JPA 10 张表设计与关联

🎯 **通俗比喻**：
> 你开了一个电商客服部门，需要准备几个文件柜。第一个柜子放"对话记录"——每个客户一个文件夹（session），里面按时间顺序放着每条聊天记录（message）。第二排柜子放"知识参考"——5 个抽屉分别放商品手册、促销单页、常见问题手册、行业报告、解决方案。第三排柜子放"工作手册"——意图列表、话术模板、业务规则。客服处理问题时，先看第一排（找历史记录），再翻第二排（查知识），按第三排（遵循规则）来回复。

📖 **技术本质**：
10 张表分三组。对话组：`cs_chat_session`（会话，PK=session_id）和 `cs_chat_message`（消息，FK=session_id），一对多关系。知识组：5 张独立表（product/activity/faq/industry/solution），不做通用模型因为字段差异大（商品有价格和规格 JSON，FAQ 有问答对），每张表都有 `vectorized` 布尔字段预留向量化。场景组：3 张表（intent/prompt/rule），预留了置信度阈值、优先级、触发关键词等配置字段。所有表通过 JPA `ddl-auto: update` 自动创建和迁移。

💭 **我的理解**：
"我一开始考虑过做一个通用的 knowledge 表，用 type 字段区分不同知识类型。但后来发现商品有 price、specifications 字段，FAQ 有 question、answer 字段，通用模型只能用 TEXT 类型的 extra_data 字段塞 JSON——查询不方便，索引也建不了。独立表虽然类多了点，但每张表结构清晰，查询简单，索引也好建。"

❓ **可能追问**：
- **"10 张表没有外键关联？为什么？"**
  → "对，没有用数据库外键，关联关系在应用层维护（比如 message 通过 sessionId 关联 session）。这是因为：JPA 的懒加载和外键约束容易产生 N+1 查询问题；而且知识表之间本身就没有关联关系，它们是独立的五类数据。"
- **"ddl-auto: update 在生产环境能用吗？"**
  → "不建议在生产用。update 模式只会新增列不会删除列，长期可能导致表结构和实体类不一致。生产环境应该用 Flyway 或 Liquibase 做数据库版本管理，用 SQL 脚本精确控制每次迁移。但在开发和教学场景下，update 模式非常方便——改个实体字段重启就自动更新表结构。"

### 深潜 11：RESTful API 设计规范（54 个接口的组织）

🎯 **通俗比喻**：
> 就像一栋写字楼的门牌号系统。一楼（/api/chat）是对话部门，二楼（/api/knowledge）是知识部门，三楼（/api/scene）是配置部门。每层楼里的房间号规则统一：大门口（GET 列表）、前台（POST 新增）、会议室（PUT 修改）、后门（DELETE 删除）。你知道了规则，就能找到任何一个房间。

📖 **技术本质**：
54 个接口按模块组织在 3 个 Controller 中。路径规范：`/api/chat/*`（对话）、`/api/knowledge/*`（知识）、`/api/scene/*`（场景）。每个模块内部按资源和操作组织：列表查询用 GET，新增用 POST，修改用 PUT，删除用 DELETE。路径常量统一定义在 `ApiConstants.java` 中避免硬编码。所有接口返回统一的 `R<T>` 响应格式（code + message + data），异常通过 `GlobalExceptionHandler` 统一处理。

💭 **我的理解**：
"54 个接口听起来很多，但按模块拆分后其实很清晰。知识模块 5 类知识 × 4 个 CRUD = 20 个，加上总览和批量操作就 25 个左右。场景模块也类似。关键是命名规范和路径统一，新接口往哪加、老接口在哪找，一看路径就知道。API 路径常量化也很重要——改一个路径只改一处，不会前后端不一致。"

❓ **可能追问**：
- **"54 个接口怎么管理的？有文档吗？"**
  → "路径统一用 ApiConstants 常量类管理，前端的 API 调用函数也按模块分文件（chat.ts/knowledge.ts/scene.ts），和后端一一对应。文档方面可以接入 Swagger/SpringDoc 自动生成 API 文档，但项目目前是靠代码结构的清晰度来保证可维护性的。"
- **"GET/POST/PUT/DELETE 的使用规范你怎么理解？"**
  → "GET 用于获取资源（幂等、不修改数据），POST 用于创建资源，PUT 用于全量更新，DELETE 用于删除。幂等性很重要——GET 和 PUT 是幂等的（调多少次效果一样），POST 不是（多次调用可能创建多条记录）。我在消息发送时用 POST + UUID 消息 ID 来避免重复提交。"

### 深潜 12：前后端分离架构

🎯 **通俗比喻**：
> 前后端分离就像餐厅的"前厅"和"后厨"分开管理。前厅（前端）负责接待客人、展示菜单、传达点单；后厨（后端）负责做菜、管理食材库存。两边通过一个"传菜窗口"（API）沟通——前厅递来一张点单，后厨做完了从窗口递出一盘菜。前厅不需要知道菜怎么做的，后厨也不关心客人坐哪桌。

📖 **技术本质**：
前端 Vue 3 + Vite 作为独立项目运行在 3100 端口，通过 Vite 的 proxy 配置把 `/api/*` 请求代理到后端 10002 端口。前端 HTTP 请求通过封装的 Axios 实例统一处理：自动加 Token、响应拦截错误、统一 loading 状态。后端通过 `WebConfig` 配置 CORS 允许跨域。数据传输使用 JSON 格式，前端定义了 TypeScript 类型（model 目录），和后端的 DTO/VO 一一对应。

💭 **我的理解**：
"前后端分离最大的好处是独立开发和部署。前端改 UI 不需要重启后端，后端改逻辑也不影响前端。而且前端技术栈和后端技术栈可以独立升级——比如前端从 Vue 2 升 Vue 3，后端完全不用动，只要 API 契约不变。缺点是多了一层网络通信开销，但现在这已经不是问题了。"

❓ **可能追问**：
- **"跨域问题怎么解决的？"**
  → "开发环境用 Vite 的 proxy 做代理，请求先到 Vite 开发服务器再转发到后端，不存在跨域。生产环境后端配置了 CORS——WebConfig 里通过 addCorsMappings 允许前端域名跨域访问，设置了允许的 Methods 和 Headers。"
- **"前后端数据格式怎么保持一致的？"**
  → "后端定义 VO（View Object）和 DTO（Data Transfer Object），前端在 model 目录里定义对应的 TypeScript interface。目前是手动同步的，如果项目更大，可以用 Swagger Codegen 从后端 API 自动生成前端类型定义。"

### 深潜 13：事务管理 @Transactional

🎯 **通俗比喻**：
> 你去银行转账——从 A 账户扣 1000，往 B 账户加 1000。如果扣完钱之后银行系统崩了，B 没加上怎么办？事务就是保证"这两步要么都成功，要么都不做"。在我的客服系统里，"保存用户消息"和"保存 AI 回复"就像转账的两步——不能只存了用户的问题但没存 AI 的回答，否则下次打开对话记录就会出现不完整的对话。

📖 **技术本质**：
`ChatService.sendMessage()` 方法标注了 `@Transactional`，整个 8 步流水线在一个事务中执行。步骤 1 保存用户消息和步骤 6 保存 AI 回复共享同一个数据库事务——如果中间任何步骤抛出未捕获的运行时异常，Spring 的事务管理器会自动回滚，两条消息都不会入库。LLM 调用的异常被 try-catch 捕获并返回 null，不会触发事务回滚，这是有意设计的——LLM 失败不应该导致整个对话流程失败。

💭 **我的理解**：
"事务的边界很重要。我把 LLM 调用的异常在 LlmService 里就 catch 掉了，返回 null 给 ChatService。这样 LLM 失败只会触发降级，不会导致事务回滚。如果 LLM 的异常不 catch，让它冒泡到 @Transactional 方法外面，那用户消息也会被回滚——但用户消息其实已经存入数据库了，回滚反而不对。"

❓ **可能追问**：
- **"@Transactional 的传播行为了解吗？"**
  → "默认是 REQUIRED——如果当前有事务就加入，没有就新建。常见的还有 REQUIRES_NEW（不管有没有都新建，独立提交）和 NESTED（嵌套事务，外层回滚内层也回滚，内层回滚外层可以 catch 住）。在我的场景下默认 REQUIRED 就够了。"
- **"如果事务太长会有什么问题？"**
  → "长事务会长时间占用数据库连接和锁资源。我的 sendMessage 方法里有 LLM 调用（网络 IO），如果 LLM 响应慢，事务持续时间就会很长。优化方案是把 LLM 调用拆到事务外——先调 LLM 拿到结果，再开事务做数据库操作。但目前项目量级不大，这个问题不突出。"

---

### 深潜 14：连接池 Druid

🎯 **通俗比喻**：
> 数据库连接就像打电话——每次打电话都要拨号、等接通、通话、挂断。如果你一天要打 1000 个电话，每次都拨号就太慢了。连接池就像你一次性开了 10 条电话线，一直不挂断（保持连接），需要打电话时直接从空闲的线上拿一条来用，用完放回去。Druid 就是这个"电话线管理员"，还附带了"通话记录"功能（SQL 监控）。

📖 **技术本质**：
Druid 是阿里开源的数据库连接池，项目中通过 `druid-spring-boot-3-starter` 集成。它预先创建一批数据库连接放在池中，应用需要时从池中获取，用完归还。相比每次 new Connection() 再关闭，省去了 TCP 握手、数据库认证等耗时操作。Druid 还提供了 SQL 监控面板，可以看到每条 SQL 的执行次数、耗时、慢查询等信息，方便性能排查。

💭 **我的理解**：
"连接池是后端几乎必备的基础设施，选 Druid 一是因为它在国内使用广泛、文档全，二是它的 SQL 监控功能在开发阶段特别有用——我可以直接看到哪些查询执行得慢，有没有 N+1 查询问题。"

❓ **可能追问**：
- **"Druid 和 HikariCP 有什么区别？"**
  → "HikariCP 是 Spring Boot 默认的连接池，性能在微基准测试中比 Druid 快，代码更简洁。Druid 的优势在于监控功能更强，有内置的 Web 面板可以看 SQL 执行详情。选择取决于需求——追求极致性能选 HikariCP，需要 SQL 监控选 Druid。"

### 深潜 15：前端四栏布局的组件化设计

🎯 **通俗比喻**：
> 四栏布局就像一个客服工作台。左边是常见问题速查手册（随手翻），中间是和客户的聊天窗口（核心工作区），右上角是产品目录（随时查产品信息），右下角是一个"思考过程记录本"（记录 AI 每一步怎么决策的）。四个区域各自独立，互不干扰，但通过"传纸条"（组件通信）协同工作。

📖 **技术本质**：
对话中心页面 `index.vue` 是一个布局容器，管理四个独立子组件的排列和通信。`QuestionSidebar.vue`（常见问题）点击后通过 emit 事件通知父组件，父组件调用 ChatInterface 的发送方法。`KnowledgeSelect.vue`（知识选择）选中的商品/活动 ID 通过 props/emit 传递给父组件，再注入到对话请求中。`AgentWorkArea.vue`（推理过程）接收对话响应中的 reasoningProcess 数组渲染 6 步推理链。组件之间不直接通信，全部通过父组件中转，符合 Vue 的单向数据流原则。

💭 **我的理解**：
"四栏布局不只是 UI 设计，更重要的是它背后的数据流。比如用户在右上角选了一个商品，这个商品 ID 要一路传到后端的 retrieveKnowledge() 方法里影响知识检索结果。这就涉及到 Vue 组件通信的设计——我用的是 props down, events up 的标准模式，没有用 Vuex/Pinia 做全局状态，因为这些数据只在这一个页面内流转，没必要全局化。"

❓ **可能追问**：
- **"组件之间如果通信层级太深怎么办？"**
  → "如果嵌套超过 2-3 层，props drilling 就很麻烦了。可以用 Vue 的 provide/inject 做依赖注入，或者用 Pinia store 做全局状态管理。我的项目只有一层嵌套（父组件→子组件），所以 props/emit 足够了。"

## 四、防雷指南

> 求职版在复试版的基础上，增加以下工程类高频陷阱题。

### 工程类高频陷阱题应对

**陷阱 1："高并发怎么办？"**

> ⭐ 别慌，这个问题考的不是你已经做了什么，而是你"知不知道该做什么"。

"高并发场景下有几个瓶颈点需要优化。第一，LLM 调用是最大的延迟瓶颈——每次调用至少几百毫秒，可以引入请求队列和限流（比如 Guava RateLimiter），同时考虑改成异步+SSE 推送。第二，知识检索目前是全表扫描，数据量大时需要加索引或接入 Elasticsearch。第三，历史消息查询可以加 Redis 缓存——同一个 session 的消息在会话期间变化不大，适合缓存。第四，连接池用的 Druid，已经在做连接复用了。当前系统已经内置了 Redis + Redisson 支持，分布式锁也有了，扩展起来有基础。"

**陷阱 2："数据库表设计为什么不用通用模型？"**

"考虑过通用模型——一个 knowledge 表加 type 字段区分类型，extra_data 用 JSON 存差异化字段。但有几个问题：JSON 字段不方便建索引和查询；每次查询都要做 JSON 解析，性能不好；代码层面也不好做类型安全。独立表虽然多了几个 Entity 类，但每张表字段清晰，查询简单，索引灵活，代码的可读性也更高。这是在'表的数量'和'代码质量'之间做的取舍。"

**陷阱 3："54 个接口怎么管理的？"**

"三个层面。路径管理：所有 API 路径定义在 `ApiConstants` 常量类中，避免字符串硬编码，改路径只改一处。代码组织：按业务模块分 3 个 Controller，每个 Controller 只管自己模块的接口。前端对齐：前端 API 调用函数也按模块分文件（chat.ts / knowledge.ts / scene.ts），和后端一一对应。如果项目再大，可以引入 Swagger 自动生成文档。"

**陷阱 4："你们团队几个人？"**

> ⭐ 如果是独立开发的，要自信地说。

"这个项目是我独立完成的——从需求分析、架构设计、数据库设计、前后端开发到测试部署。独立开发让我对系统的每个环节都有完整的理解，比如为什么选双引擎降级、为什么知识表独立设计、8 步流水线每步的输入输出是什么。当然，真实的生产项目肯定需要团队协作，到时候代码评审、分支管理、CI/CD 这些流程都是必要的。"

## 五、技术亮点速查卡

> ⭐ 面试中可以主动抛出的亮点，不用等面试官问。用一句话钩住他的兴趣，让他主动追问。

### 亮点 1：8 步对话流水线

**钩子句**："一条用户消息从进入系统到生成回复，要走 8 个处理步骤，像工厂流水线一样串联。"

面试官一追问，你就展开：保存消息→LLM 分析（意图/场景/情绪）→知识检索（优先级 5 步）→多轮上下文构建（最近 10 条历史消息）→LLM 生成回复→卡片类型选择→推理过程构建→响应返回。每步有明确的输入输出和日志。

### 亮点 2：双引擎无感降级

**钩子句**："LLM 挂了用户感觉不到——系统自动切到关键词规则引擎，回复质量下降但服务不中断。"

面试官一追问，你就展开：两个降级点（分析和回复各一个），通过 null 返回值做切换，全链路异常 catch 不冒泡，日志标注引擎类型方便排查。

### 亮点 3：推理过程可视化

**钩子句**："每次对话，前端都能看到 AI 的完整推理链——6 个步骤、每步用了什么引擎、检索到了什么知识。"

面试官一追问，你就展开：6 步推理链（输入解析→场景识别→意图分析→情绪判断→知识检索→生成回复），每步标注了分析引擎是 LLM 还是关键词，知识检索展示命中的商品和匹配分数。前端 AgentWorkArea.vue 组件实时渲染。

### 亮点 4：知识约束的 LLM 输出

**钩子句**："大模型最怕幻觉——编造不存在的商品和优惠。我用知识检索来约束它，让它基于真实数据回答。"

面试官一追问，你就展开：先从数据库检索商品/活动/FAQ → buildKnowledgeText() 格式化 → 注入系统提示词 → Prompt 里明确要求"基于提供的知识回答" → 减少幻觉。

### 亮点 5：两次 LLM 调用 + 不同温度策略

**钩子句**："一次对话调了两次 LLM，干的事完全不同——第一次做'选择题'用低温度，第二次做'写作文'用高温度。"

面试官一追问，你就展开：analyzeUserInput() 用 temperature 0.1、max_tokens 150 做结构化分析；generateReply() 用 temperature 0.7、max_tokens 500 做自然语言生成。同一个模型、不同参数、不同效果。

## 六、故事线自洽包（求职版补充）

> 求职面试的故事线更偏"工程实践"，在复试版的基础上补充以下角度。

### 为什么选这个技术栈？

"Spring Boot 3 是 Java 后端的主流框架，企业用得最多，选它是为了贴近真实工作环境。JPA 而不是 MyBatis 是因为项目重点是业务逻辑而不是复杂 SQL，JPA 的自动建表能加速开发。前端选 Vue 3 + TypeScript 是因为它现在是国内前端最主流的技术栈之一，Element Plus 有丰富的企业级组件。LLM 接入选 OneRouter 网关是因为它兼容 OpenAI 协议，以后想换模型改一行配置就行。"

### 如果让你重新做一次，你会改什么？

"有三个地方。第一，知识检索我会直接上向量数据库，而不是先做关键词匹配——虽然关键词方案能跑通流程，但语义理解能力太弱了。第二，LLM 调用我会改成异步 + SSE 流式输出，现在同步等待的延迟体验不好。第三，场景配置模块我会真正接入对话链路——让意图和提示词从数据库动态加载，而不是代码硬编码。这三个都是我在开发过程中意识到的问题，但受限于时间没有做。"

### 你在这个项目里学到最多的是什么？

"做 AI 应用和做传统应用最大的区别是'不确定性管理'。传统应用的逻辑是确定的，同样的输入一定得到同样的输出。但大模型的输出有随机性、有幻觉风险、有 API 不稳定的问题。所以你需要在每个环节都考虑'如果这步出了问题怎么办'——这就是我做双引擎降级的动力。这个思维方式对我做其他类型的系统也有帮助。"
