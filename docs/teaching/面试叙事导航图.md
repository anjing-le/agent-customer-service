# 可靠 Agent 客服系统 - 面试叙事导航图

这份导航图用于把项目讲成一个自洽的故事：它不是“套模型聊天”，而是一个从 `infra-dev-scaffolding` 生长出来的可靠客服 Agent。

核心表达：

```text
脚手架工程习惯
  + 客服 Agent 领域模型
  + RAG 证据约束
  + 规则兜底
  + 知识缺口和转人工闭环
  = 可靠 Agent 客服系统
```

## 一、30 秒开场

### 版本 A：工程可靠性

> 我做了一个可靠 Agent 客服系统。它的重点不是让 AI 什么都回答，而是把客服场景里的边界做清楚：有知识证据才回答，没有证据就兜底并记录知识缺口，遇到投诉、催办、法律风险或人工诉求就转人工。工程上完全继承脚手架技术栈：前端 React + TypeScript + Vite，后端 Go 标准库 HTTP，数据层 PostgreSQL + pgx + SQL migration。

### 版本 B：AI 产品边界

> 很多 AI 客服 demo 看起来能聊，但真正上线会遇到两个问题：模型可能幻觉，外部能力也可能不稳定。我这个项目关注的是怎么把 Agent 做可靠：回复要绑定知识证据，无证据要沉淀运营任务，高风险要交给人工，并且所有链路都能在控制台看到和处理。

### 版本 C：教学定位

> 这个项目是从统一脚手架里长出来的教学案例。底层技术和习惯不需要重新学，学生只关注 Agent 客服怎么设计：会话、知识、规则、缺口、工单、控制台和 API 边界。

## 二、三条主线

### 主线 A：从业务问题讲

适合回答：“介绍一下你的项目。”

```text
电商客服重复咨询多
  -> 纯人工成本高，纯规则体验差
  -> Agent 可以提升效率，但不能乱答
  -> 用知识文章作为回答证据
  -> 无证据生成 knowledge_gap
  -> 高风险生成 transfer_ticket
  -> 控制台让运营处理缺口和工单
```

关键句：

- “我不是让 Agent 尽量回答，而是让它知道什么时候不能回答。”
- “防幻觉不是一句 prompt，而是一套数据和流程边界。”
- “知识缺口让系统从‘不知道’进入运营闭环。”

### 主线 B：从技术架构讲

适合回答：“系统架构怎么设计？”

```text
apps/console
  React 控制台
      |
      v
cmd/platform-all
  Go HTTP API
      |
      +-- internal/customer   会话、消息、回复策略
      +-- internal/knowledge  知识文章、检索、缺口处理
      +-- internal/ops        指标、规则测试、转人工处理
      |
      v
internal/platform/store.Runtime
      |
      +-- Store          内存演示与测试
      +-- PostgresStore  真实持久化
```

关键句：

- “业务 handler 只依赖 `Runtime` 接口，不直接关心数据库实现。”
- “内存存储用于课堂快速演示，PostgreSQL 存储用于生产式持久化。”
- “SQL migration 让数据模型本身成为教学材料。”

### 主线 C：从可靠 Agent 讲

适合回答：“这个项目最有亮点的地方是什么？”

```text
用户发消息
  -> 保存用户消息
  -> 搜索 knowledge_articles
  -> 有证据：rag+rule 回复，写 evidence_ids
  -> 无证据：NO_EVIDENCE_FALLBACK，创建 knowledge_gap
  -> 高风险：TRANSFER_THRESHOLD，创建 transfer_ticket
  -> 更新 conversation 状态
```

关键句：

- “回复策略围绕证据、风险和运营闭环展开。”
- “规则不是替代 Agent，而是给 Agent 加护栏。”
- “转人工不是失败，而是可靠系统必须具备的边界。”

## 三、深潜点

### 深潜 1：为什么用脚手架技术栈

通俗说法：

> 这个项目不是另起炉灶，而是在统一地基上盖客服 Agent 这层楼。学生不需要同时学习多套技术，只需要观察业务设计怎么长出来。

技术本质：

- 前端：React + TypeScript + Vite
- 后端：Go + `net/http` + `ServeMux`
- 数据：PostgreSQL + pgx + SQL migration
- 配置：环境变量优先
- 日志：结构化日志
- 质量门禁：脚本检查、Go test、Vite build

可能追问：

**Q: 为什么不用更重的后端框架？**

**A:** 教学项目要让边界显式。Go 标准库 HTTP 足够表达路由、handler、JSON 和错误处理，学生能直接看到请求怎么流转。

### 深潜 2：Runtime 接口

通俗说法：

> `Runtime` 像客服系统的插座。上面插内存存储也能跑，插 PostgreSQL 也能跑，前端和 API 不需要换。

技术本质：

`Runtime` 定义了会话、消息、知识、缺口、规则、工单和 dashboard 的统一能力。`Store` 和 `PostgresStore` 实现同一套接口。

可能追问：

**Q: 这样设计的好处是什么？**

**A:** 一是测试简单，内存实现可以快速验证业务逻辑；二是部署真实，PostgreSQL 实现可以落库；三是边界清晰，后续接模型、向量检索或缓存时不会污染 handler。

### 深潜 3：RAG 证据约束

通俗说法：

> Agent 回答前要先翻知识手册。手册里有就按手册回答，手册里没有就承认不知道并记录下来。

技术本质：

`SearchKnowledge` 从知识文章标题、分类、正文、标签里匹配用户问题。命中后 Agent 回复带上 `evidence_ids`；未命中则创建 `KnowledgeGap`。

可能追问：

**Q: 关键词检索是不是简单？**

**A:** 是简单，但这是 V1 的有意选择。先用可解释检索把可靠链路跑通，再升级 PostgreSQL 全文检索或 embedding 向量检索。重点是证据可追踪，而不是一开始堆复杂组件。

### 深潜 4：防幻觉设计

通俗说法：

> 防幻觉不是告诉模型“别乱说”，而是系统不给它乱说的机会。

技术本质：

- 没有 evidence 时不自由回答。
- 创建 `knowledge_gaps`。
- 回复里标记 `FallbackReason = NO_EVIDENCE`。
- 控制台支持关闭缺口或从缺口创建知识文章。

可能追问：

**Q: 为什么要做知识缺口？**

**A:** 缺口是运营闭环的入口。它把一次回答失败转成可处理任务，让系统知识库持续变好。

### 深潜 5：转人工边界

通俗说法：

> 有些问题不是 Agent 应该硬扛的，比如投诉、法律风险、连续催办。可靠系统要知道什么时候交给人。

技术本质：

`TRANSFER_THRESHOLD` 命中后，系统创建 `transfer_ticket`，Agent 返回转人工话术，不再自由承诺处理结果。

可能追问：

**Q: 转人工会不会显得系统弱？**

**A:** 不会。对客服系统来说，错误承诺比转人工更危险。转人工是风险控制能力，不是能力不足。

### 深潜 6：规则兜底

通俗说法：

> 规则像护栏，平时不抢方向盘，但车快开出边界时必须拦住。

技术本质：

`evaluateRules` 默认允许回答；空输入、高风险、无证据会分别命中拒绝、转人工、无证据兜底。控制台通过 `/api/ops/rules/test` 演示规则结果。

可能追问：

**Q: 后续规则怎么升级？**

**A:** 可以把规则表达式、优先级、版本和启停都外置到数据库，并增加审计、灰度和回放测试。

### 深潜 7：PostgreSQL 事务

通俗说法：

> 一次消息处理不能只存用户问题，不存 Agent 回复；也不能只建了工单，没更新会话状态。

技术本质：

`PostgresStore.SendMessage` 使用事务保存用户消息、Agent 消息、知识缺口、转人工工单和会话状态。失败时整组操作回滚。

可能追问：

**Q: 为什么不用自动建表？**

**A:** SQL migration 更适合教学和生产。表结构、字段、约束都清楚，能让学生直接理解领域模型。

### 深潜 8：前端控制台

通俗说法：

> 前端不是聊天玩具，而是坐席和运营的工作台。

技术本质：

控制台包含指标、会话队列、消息发送、证据展示、知识缺口处理、规则测试、转人工工单处理。它把 Agent 的决策结果变成可操作流程。

可能追问：

**Q: 为什么不做一个普通聊天页？**

**A:** 因为客服 Agent 的价值不只在回复，还在运营闭环。普通聊天页看不到证据、缺口、规则和工单。

## 四、防雷指南

### 不要这样说

| 不建议 | 建议 |
|--------|------|
| “这是一个聊天机器人” | “这是可靠 Agent 客服系统” |
| “AI 会回答用户问题” | “有证据才回答，无证据兜底，高风险转人工” |
| “用了某个模型” | “模型只是能力之一，关键是证据、规则和运营闭环” |
| “后端随便写了 API” | “API 继承脚手架风格，并按 customer、knowledge、ops 分边界” |
| “关键词检索比较简单” | “V1 用可解释检索跑通链路，V2 再升级向量检索” |

### 高频追问

**Q: 和普通 AI 客服 demo 的区别？**

**A:** 普通 demo 往往只关注能不能回答。这个项目关注能不能可靠运行：证据约束、防幻觉、规则兜底、转人工、知识缺口、真实持久化和控制台运营。

**Q: 当前最大不足是什么？**

**A:** V1 还没有真正接入模型生成、向量检索和流式输出，多轮上下文也还可以用于查询改写。现在先把可靠边界打稳，后续逐步增强智能程度。

**Q: 如果继续做，优先做什么？**

**A:** 优先级是：接入模型客户端并保留证据边界，升级全文或向量检索，加入 SSE 流式回复，增加对话质量评估和规则版本管理。

**Q: 高并发怎么考虑？**

**A:** 数据库层做索引、分页和连接池参数；检索层做缓存和异步向量化；模型层做限流、超时、队列和熔断；规则前置减少不必要的模型调用。
