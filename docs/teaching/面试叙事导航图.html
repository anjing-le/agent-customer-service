可靠 Agent 客服系统 - 面试叙事导航图

这份页面是 Markdown 导航图的轻量 HTML 版，用于课堂投屏和面试速览。主线是：项目从统一脚手架生长出来，业务重点是可靠客服 Agent 的边界设计。

30 秒开场

我做了一个可靠 Agent 客服系统。它不是让 AI 什么都回答，而是有知识证据才回答，没有证据就兜底并记录知识缺口，遇到投诉、催办、法律风险或人工诉求就转人工。工程上继承脚手架技术栈：React + TypeScript + Vite，Go 标准库 HTTP，PostgreSQL + pgx + SQL migration。

核心表达

脚手架工程习惯
  + 客服 Agent 领域模型
  + RAG 证据约束
  + 规则兜底
  + 知识缺口和转人工闭环
  = 可靠 Agent 客服系统

三条主线

业务问题

关键词：重复咨询、证据回答、知识缺口、人工工单。

链路图

用户发消息
  -> 保存 user message
  -> 搜索 knowledge_articles
  -> 有证据：rag+rule 回复，写 evidence_ids
  -> 无证据：创建 knowledge_gap，安全兜底
  -> 高风险：创建 transfer_ticket，转人工
  -> 更新 conversation 状态
  -> 控制台展示证据、缺口、规则和工单

深潜速查

问题回答方向
为什么用脚手架技术栈？统一底层习惯，让学生只关注 Agent 客服设计。
Runtime 接口有什么价值？隔离内存演示和 PostgreSQL 持久化，handler 不关心存储实现。
如何防幻觉？证据优先，无证据不自由回答，生成知识缺口。
为什么转人工？高风险客服问题不能由 Agent 随意承诺，转人工是可靠边界。
后续怎么升级？模型客户端、全文或向量检索、SSE 流式回复、规则版本管理。
不要把项目讲成“聊天机器人”。更准确的说法是：可靠 Agent 客服系统。
