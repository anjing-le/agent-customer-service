开场锚点

30秒，一句话抓住注意力
⭐ 推荐
风格A：痛点驱动型
我自己网购比较多，经常遇到客服机器人只会回固定话术——你问"有什么优惠"，它回你一大段不相关的模板。我就想，能不能做一个真正"懂"客户问题的客服？于是做了这个智能电商客服系统，用大模型理解意图、用知识库约束回答、用规则引擎做降级兜底。
老师喜欢有好奇心的学生。"发现问题→产生疑问→动手解决"的链条自然不做作。
备选
风格B：技术好奇型
大模型直接用在客服场景有几个问题——幻觉会编造信息、API 不稳定会超时。我就想能不能做一个"大模型+知识库+规则兜底"的三层架构？做了这个电商客服系统，从意图识别到知识检索到双引擎降级，把整条链路都跑通了。
直接点出行业痛点，展示对技术趋势的了解。适合面对偏工程导向的导师。
备选
风格C：对比思考型
一个比喻——普通客服机器人像背课文，固定话术匹配关键词。我做的像请了个聪明顾问——先理解你想干什么，再查知识库找答案，最后组织语言回答。而且大模型挂了还能自动切到规则引擎，保证服务不中断。
生活化比喻让任何背景的老师都能秒懂。"背课文 vs 聪明顾问"的对比很直观。

主线路径

三条路线，根据问题灵活切入
路线A：从"解决了什么真实问题"出发

适合回答："介绍一下你的项目" / "这个项目做什么的"

① 我的方案 → ② 双引擎设计 → ③ 8步流水线 → ④ 推理可视化 → ⑤ 扩展方向
节点说什么面试官心理
① 我的方案把大模型和知识库结合，让 AI 基于真实数据回答问题思路清晰，知道 LLM 不能裸用
② 双引擎设计大模型 API 随时可能挂，做了双引擎——LLM 挂了自动切关键词规则引擎有工程意识，知道系统要可靠
③ 8步流水线一条消息进来要走 8 步：保存→分析意图→检索知识→生成回复→...，像工厂流水线看得出做得比较深入，不是随便套了个 API
④ 推理可视化每次对话的推理过程都透明展示，用户能看到 AI 是怎么思考的有可解释性意识，这在 AI 研究中很重要
⑤ 扩展方向知识表预留了 vectorized 字段，为后续接入向量数据库做语义检索做准备有技术规划能力，不只是做了当下的功能
路线B：从"双引擎降级设计"出发

适合回答："你觉得最有挑战的部分是什么" / "遇到的难点"

① 问题严重性 → ② 降级方案 → ③ 技术实现 → ④ 可观测性 → ⑤ 引申思考
节点说什么面试官心理
① 问题严重性大模型 API 有三个不稳定因素：网络超时、限流、Key过期。任何一个都会让用户等半天有问题分析的习惯，不是遇到问题就绕开
② 降级方案两个降级点：分析阶段LLM挂了走关键词识别，回复阶段LLM挂了走模板拼接方案有层次，不是一个简单的 if-else
③ 技术实现所有 LLM 调用都 catch 异常返回 null，调用方通过 null 判断走哪个引擎代码层面考虑得很细
④ 可观测性日志里标注了分析引擎=LLM还是关键词，回复引擎=LLM还是规则，方便排查有运维意识，知道线上系统需要可观测
⑤ 引申思考这让我意识到，做 AI 应用和做传统应用最大的区别就是"不确定性管理"能从具体问题抽象出一般性认知，有研究潜力
路线C：从"AI + 传统工程的融合"出发

适合回答："你对大模型/AI有什么看法" / "为什么选这个方向"

① AI裸用问题 → ② 知识约束 → ③ 工程化考量 → ④ 温度选择 → ⑤ 学到什么
节点说什么面试官心理
① AI裸用问题大模型最大的问题是幻觉——它会一本正经地编造信息。客服场景下这是致命的对 AI 局限性有认识，不是盲目追捧
② 知识约束用知识检索来约束——先从数据库找到真实数据，注入提示词让 AI 基于事实回答了解 RAG 的基本思想
③ 工程化考量光有 AI 不够，还需要事务管理、异常处理、分层架构、连接池这些传统工程能力技术视野比较全面
④ 温度选择分析意图用 temperature 0.1 要确定性，生成回复用 0.7 要创造性——同一个模型不同任务参数不同对模型参数有理解，不是黑盒调用
⑤ 学到什么AI 应用的本质是"用确定性工程包裹不确定性模型"——这也是我想继续深入研究的方向有提炼、有方向感，适合做研究

深潜知识点

每个概念三层递进：比喻秒懂 → 技术准确 → 个人思考
1
意图识别（LLM vs 规则引擎）
▼
🎯 通俗比喻

想象你开了一家餐厅，门口站了两个迎宾。第一个是一个特别聪明但偶尔迟到的人（LLM），他一看客人的表情和穿着就知道"这位想吃商务套餐"。第二个是一个很靠谱但比较死板的人（规则引擎），他只会看客人手里拿的菜单牌——牌上写"商务"就带去商务区。正常情况聪明迎宾上班就用他，他迟到了就让靠谱迎宾顶上，客人不能在门口站着。

📖 技术本质

意图识别就是搞清楚用户"想干什么"。LLM 路径是把用户消息连同 Prompt 发给大模型，要求返回结构化 JSON（场景、意图编码、置信度、情绪），temperature 设 0.1 保证确定性。规则路径用 containsAny() 做关键词匹配——消息里包含"优惠、打折、促销"就判定为"商品优惠查询"意图，覆盖 5 种核心意图和 30+ 情绪关键词。

💭 我的理解
"我一开始觉得有了大模型还要什么关键词匹配，后来 API 超时了一次就想明白了——生产系统不能有单点故障。关键词匹配虽然笨，但它快、稳定、不花钱。这就是工程里常说的'优雅降级'——能用好的就用好的，好的不行就用能用的。"
❓ 可能追问
Q: LLM 做意图识别和传统分类模型（比如 BERT）比有什么优劣？
LLM 优势是零标注数据、理解能力强，劣势是延迟高、成本高、输出不完全可控。BERT 分类器准确率更高更稳定，但需要大量标注数据训练。真正上生产可能 BERT 做主力、LLM 做兜底。
Q: 你的关键词列表怎么确定的？覆盖率够吗？
根据电商最常见的 5 类场景手动梳理。覆盖率不完美，没匹配上的统一归为"通用咨询"。提升方案：从真实对话日志统计高频词动态补充，或从数据库表加载——cs_scene_intent 表已经建好了。
2
双引擎降级 / 容错设计
▼
🎯 通俗比喻

就像高速公路和国道的关系。正常情况走高速（LLM），又快体验又好。但高速可能封路（API 超时）、限行（限流）、收费站坏了（Key 过期）。这时候导航自动切到国道（规则引擎），虽然慢点、景色差点，但目的地一样能到。关键是——切换过程对乘客（用户）是无感的。

📖 技术本质

系统有两个降级切换点。分析阶段：LlmService.analyzeUserInput() 失败返回 null，ChatService 切到三个 fallback 方法（场景、意图、情绪各一个）做关键词匹配。回复阶段：LlmService.generateReply() 失败返回 null，切到规则引擎做模板拼接。所有 LLM 调用套 try-catch，任何异常吞掉返回 null，降级由调用方控制。

💭 我的理解
"双引擎的核心不是'两套代码'，而是'一个承诺'——不管后面怎么出错，用户永远能得到一个回复。最好的容错设计是用户感知不到容错在发生。日志里标注了用的哪个引擎，但用户界面上看不出区别。"
❓ 可能追问
Q: 降级后回复质量差了怎么办？
有总比没有好。规则引擎回复的是标准话术，信息准确度反而更高。还可以加"引擎标识"——降级模式自动追加"如需进一步帮助请联系人工客服"，把期望管理好。
Q: 除了返回 null，还有什么降级策略？
超时降级——设 3 秒阈值，超了就切换。熔断器模式——连续 5 次失败直接跳过 LLM 一段时间。Spring Cloud 的 Resilience4j 可以做。
3
知识检索（关键词匹配 vs 语义检索）
▼
🎯 通俗比喻

去图书馆找书。关键词匹配就像翻卡片目录——找"运动鞋"就一张张翻有没有这三个字。语义检索就像问一个读过全馆书的图书管理员——你说"跑步穿的舒服的鞋"，虽然你没说"运动鞋"，但他懂你的意思。我目前用的是翻卡片，但每张卡片上预留了"管理员读书笔记"的位置（vectorized 字段），以后可以升级。

📖 技术本质

采用关键词子串匹配算法 calculateMatchScore()：先做单字符命中统计，再做 2-6 字符连续子串匹配（连续子串权重更高），归一化到 [0,1]，阈值 0.3 以上才算命中，取 Top 3。检索优先级：前端手动选择(score=0.99) > 自动匹配商品 > 自动匹配活动 > FAQ 匹配。

💭 我的理解
"关键词匹配是有意识的选择。核心目标是展示'大模型+知识库'的架构思路，不是做一个完美的搜索引擎。先用简单方案跑通全链路，预留升级接口——这是'先让它 work，再让它 work better'的原则。"
❓ 可能追问
Q: 关键词匹配有什么缺陷？举个例子？
不理解语义。用户问"有没有适合送女朋友的礼物"，匹配不到任何商品名，但"香水""丝巾"可能都是好推荐。语义检索能理解"送女朋友"和"礼品类商品"的语义关联。
Q: 如果要升级成语义检索怎么做？
三步：① 用 Embedding 模型把知识库描述转成向量存到向量数据库；② 用户消息也转向量做余弦相似度匹配；③ 结果同样注入提示词。vectorized 字段就是为这个预留的。
4
多轮对话与上下文管理
▼
🎯 通俗比喻

打电话给客服，第一个问题"你们有什么运动鞋？"，第二个问题"那它多少钱？"。如果每次不同客服接（单轮），第二个客服不知道"它"是什么。多轮对话就是让同一个客服一直在线，他记得你之前问了什么。但记忆力有限——最多记最近 10 条消息，太早的忘了，不然脑子装不下（Token 超限）。

📖 技术本质

通过数据库 + LLM messages 数组实现。每条消息存入 cs_chat_message 表，带 sessionId 做会话隔离。生成回复前从数据库取同 session 最近 10 条历史消息，注入到 messages 数组：[system 提示词, ...历史消息, 当前 user 消息]，这是 OpenAI Chat Completions API 的标准多轮格式。

💭 我的理解
"多轮对话看起来简单但要权衡很多。传多少条？多了 Token 贵、延迟大；少了上下文不够。我选 10 条——客服场景一般几轮就解决了。用数据库存历史而不是内存——用户关页面再打开，历史记录还在。"
❓ 可能追问
Q: 10 条够不够？怎么确定的？
经验值。电商客服通常 3-5 轮解决问题，10 条覆盖 2-3 个连续话题。更科学的方法是统计真实对话轮次分布。也可以做动态窗口——超阈值时做摘要压缩。
Q: 指代消解怎么处理？
目前靠 LLM 自身理解——历史消息有上下文，大部分情况能推断。更好方案是加实体追踪模块，记住当前对话核心实体，后续轮次自动关联。
5
Prompt Engineering（系统提示词设计）
▼
🎯 通俗比喻

你招了一个超级聪明的实习生（大模型），但他刚来什么都不了解。你写了一份"岗位说明书"（System Prompt），上面写着角色、规矩、什么能说什么不能说。然后每次有客户来，再给他一张"速查小纸条"（增强提示词）——客户在问优惠、心情不太好、相关商品信息……有了说明书+小纸条，实习生就能给出靠谱回答了。

📖 技术本质

系统提示词分两层。基础层是 SYSTEM_PROMPT 常量，定义角色和 6 条行为规则。增强层是 buildEnhancedPrompt() 动态拼接：当前场景类型、用户意图、用户情绪（负面追加安抚指令）、检索到的知识。两次 LLM 调用的 Prompt 完全不同：分析用 Prompt 要求输出 JSON，生成回复用 Prompt 要求输出自然语言。

💭 我的理解
"Prompt 工程看起来是'写作文'，其实更像'写合同'——每个条款写清楚，不然对方（模型）会按自己理解来。比如写了'返回纯 JSON'，有些模型还是包 markdown 代码块，代码里要额外处理。好的 Prompt 不只是'写出来'，还要反复测试调整。"
❓ 可能追问
Q: 提示词迭代了几版？
最初只有角色设定，LLM 常跑题编造。加了"基于知识回答"减少幻觉。又加了情绪判断和安抚指令。最终 6 条规则+动态上下文，迭代了 4-5 版。
Q: Few-shot 和 Zero-shot 区别？你用的哪种？
Zero-shot 直接告诉模型做什么不给示例；Few-shot 给几个输入-输出示例。目前用 Zero-shot，分析任务简单模型能理解。复杂场景可改 Few-shot 提高格式稳定性。
6
LLM 幻觉问题与知识约束
▼
🎯 通俗比喻

大模型就像一个记忆力超强但有时分不清"记住的"和"脑补的"的人。你问"这双鞋打几折"，他可能自信地说"打七折"——但根本没有这个折扣，是他编的。解决办法是给他一张 cheat sheet（小抄）——把真实折扣写上递给他，告诉他"只能按纸上的信息回答"。这就是知识检索+注入提示词在做的事。

📖 技术本质

幻觉（Hallucination）是大模型生成看似合理但事实不正确内容的现象。项目通过 RAG 简化版缓解：先从数据库检索真实数据，通过 buildKnowledgeText() 格式化为结构化文本，注入系统提示词的"参考知识"部分，并明确要求"基于提供的知识信息回答，禁止编造不存在的商品和活动"。

💭 我的理解
"幻觉本质是因为 LLM 是概率模型——不是在'查询事实'，是在'预测最可能的下一个词'。知识注入相当于给概率分布加了一个先验约束——提示词里有了真实数据，模型大概率基于这些数据回答。但不是 100% 有效，极端情况模型还可能无视约束。"
❓ 可能追问
Q: 除了知识注入，还有什么方法减少幻觉？
降低 temperature 让输出更确定；加后处理校验——生成后检查商品名、价格是否真实存在；用 RLHF 微调模型让它更守规矩（超出项目范围）。
Q: 怎么验证知识约束是有效的？
对比测试——有无知识注入的回复对比；推理可视化——前端展示命中了哪些数据，人工核实回复是否与数据一致。
7
Temperature 参数在不同场景的选择
▼
🎯 通俗比喻

Temperature 就像创作的"自由度旋钮"。调到最低（0-0.2），大模型像严谨的会计——1+1 永远是 2，不会创新也不会出错。调到中间（0.5-0.8），像文案写手——同一主题写出不同版本，有创意又不离谱。调到最高（1.5+），像喝了酒的诗人——可能蹦出天才灵感，也可能胡言乱语。

📖 技术本质

Temperature 控制 softmax 函数的输出概率分布。值越低概率集中在最高概率 token，输出越确定；值越高概率越分散，输出越随机。项目两次调用用不同温度：analyzeUserInput() 用 0.1（稳定 JSON 输出），generateReply() 用 0.7（自然多样的回复）。

💭 我的理解
"temperature 选择本质是'准确性'和'多样性'的权衡。意图分析像选择题，答案应该确定，用低温度。生成回复像写作文，同一意思可以多种表达，用适中温度。没有'最佳值'，取决于场景，要实际测试。"
❓ 可能追问
Q: temperature 0 和 0.1 有区别吗？
0 理论上每次输出完全一样，但 OpenAI 说实际不保证完全确定性。0.1 基本也高度确定，留一点点灵活性。实际效果差别很小。
Q: 负面情绪时 temperature 要不要调？
有意思的想法。负面场景需要更谨慎回复，可以调低到 0.4-0.5 减少"说错话"风险。目前没做动态调整，但确实是有价值的优化方向。
8
对话系统的评估方法
▼
🎯 通俗比喻

评估客服好不好，像评一家餐厅。不能只看"有没有上菜"（系统有没有回复），还要看"菜品对不对"（回答准确吗）、"上菜快不快"（响应延迟）、"服务态度好不好"（语气友好吗）、"推荐对的菜没"（意图识别正确吗）。最重要的是——客人吃完会不会再来（用户满意度）。

📖 技术本质

评估维度：意图识别准确率、知识检索召回率和精确率、回复相关性和流畅性、响应延迟、用户满意度。项目通过日志记录每次对话的分析引擎类型、意图结果、知识检索命中数和匹配分数、回复引擎类型。前端推理过程可视化支持人工审查。

💭 我的理解
"评估是 AI 对话系统最难的部分之一。传统软件有'标准答案'，但 AI 回复没有唯一正确答案。所以自动化指标+人工评估都必不可少。推理过程可视化就是为人工审查设计的——评估者看到 AI 每步决策，判断'这步做对了没'。"
❓ 可能追问
Q: 如果让你设计评测方案怎么做？
三层：① 自动化——100 条标注测试用例跑意图准确率；② 半自动化——系统回答后人工打 1-5 分；③ 用户调研——上线后收集评分反馈。还可以 A/B 测试——LLM vs 规则引擎对比满意度。
Q: 你有跑过什么评测吗？
测试了双引擎降级——关闭 LLM 验证系统正常走规则引擎。也测试了不同类型问题的意图识别。系统化大规模评测还没做，是后续方向。

故事线自洽包

让你的故事逻辑自洽、真实可信
🎯 为什么选客服方向？
"其实起因挺朴素的。我自己网购比较多，经常遇到客服机器人只会回固定话术的情况——你问一句'有什么优惠'，它回你一大段不相关的模板。后来 ChatGPT 出来之后，我就想试试，能不能做一个真正'懂'客户问题的客服。电商客服场景还有个好处——需求明确、知识边界清晰（就是那些商品和活动数据），特别适合练手大模型应用。"
🔧 遇到的真实挑战
挑战 1：8 步流水线的设计
"一开始我想的是'接到消息→调 LLM→返回回复'，三步完事。但做着做着发现不行——LLM 回复质量取决于你给它什么信息。所以我加了意图分析、知识检索、上下文构建这些步骤。最终变成了 8 步，每一步的输出是下一步的输入。"
挑战 2：LLM 返回 JSON 的不确定性
"让 LLM 返回结构化 JSON 比想象中难。有时候它会在 JSON 外面包一层 markdown 代码块，有时候字段名大小写不一致。我在代码里写了好几层解析逻辑——先去掉 markdown 包裹，再做 JSON parse，parse 失败就返回 null 走兜底。"
挑战 3：关键词匹配算法的调优
"最初用的是简单的 contains() 判断，太粗糙——用户输入'运动鞋推荐'会匹配到所有包含'运'字的商品。后来改成连续子串匹配+加权，连续匹配'运动鞋'三个字的得分远高于只匹配到一个'运'字的。还加了 0.3 阈值过滤低相关结果。"
💡 "双引擎"这个设计是怎么想到的？
"有次在本地调试的时候，LLM API 突然超时了，大概等了 10 秒页面才报错。我当时就想——如果这是上线了的系统呢？用户等 10 秒看到报错，体验直接崩了。然后我想到了'优雅降级'——LLM 的备选方案是什么？就是传统的关键词规则引擎。虽然没有 LLM 那么智能，但起码能给用户一个有用的回复。所以我就设计了双引擎——LLM 是主引擎、规则是备引擎，切换过程对用户无感。"
🤝 被问"这代码是你写的吗"？
"是我独立开发的。当然开发过程中我会参考技术文档和开源项目的实现思路，也会用 AI 工具帮我查文档和排 Bug。但架构设计——比如为什么做双引擎、为什么用 8 步流水线、知识检索的优先级怎么定——这些是我自己思考的。代码里每个设计决策我都能讲清楚为什么这么做。"
⭐ 坦诚但自信。承认参考了资料是正常的，重要的是你能说清楚为什么这样做、遇到了什么问题、怎么解决的。

9
Spring Boot 分层架构
▼
🎯 通俗比喻

像一家公司的组织架构。Controller 是前台接待——接电话、记客户要求、转给部门。Service 是业务部门——真正干活。Repository 是档案室——存取数据。Config 是行政部——配置规章制度。大家各干各的，前台不需要知道档案室怎么管文件。

📖 技术本质

标准三层架构。Controller 层（3个）负责接收请求、参数校验、返回统一响应 R<T>。Service 层（4个）负责核心业务逻辑。Repository 层（10个）继承 JpaRepository 提供标准 CRUD。横切关注点通过 AOP 切面处理：ControllerLogAspect 记录请求日志，FacadeAspect 统一参数校验和异常处理。

💭 我的理解
"分层的核心好处是解耦。比如要把知识检索从关键词换成向量检索，只改 Service 层，Controller 和 Repository 完全不用动。AOP 切面也一样——加请求耗时统计，不需要在每个 Controller 方法里写，加个切面统一处理。"
❓ 可能追问
Q: 为什么用 AOP 做日志？
不侵入业务代码，Service 只关注业务逻辑；统一管理，所有 Controller 请求日志格式一致，修改只改一处。这就是 AOP 的核心价值——横切关注点集中管理。
Q: @Facade 注解是干什么的？
自定义组合注解，把参数校验和异常处理绑在一起。加了 @Facade 就自动校验参数、出异常自动包装成统一响应格式，减少模板代码。
10
JPA 10 张表设计与关联
▼
🎯 通俗比喻

开了个客服部门准备文件柜。第一排"对话记录"——每个客户一个文件夹（session），按时间放聊天记录（message）。第二排"知识参考"——5个抽屉分放商品手册、促销单页、FAQ手册、行业报告、解决方案。第三排"工作手册"——意图列表、话术模板、业务规则。

📖 技术本质

10 张表分三组。对话组：cs_chat_session 和 cs_chat_message（一对多）。知识组：5 张独立表（字段差异大所以不做通用模型），每张有 vectorized 布尔字段。场景组：3 张表预留置信度阈值、优先级等配置。所有表 JPA ddl-auto: update 自动创建。

💭 我的理解
"考虑过通用 knowledge 表用 type 字段区分。但商品有 price/specifications，FAQ 有 question/answer，通用模型只能用 TEXT 塞 JSON——查询不便、索引建不了。独立表虽然类多，但结构清晰、查询简单、索引灵活。"
❓ 可能追问
Q: 10 张表没有外键？
关联在应用层维护。JPA 懒加载和外键容易产生 N+1 查询问题；知识表之间本身没关联，是独立五类数据。
Q: ddl-auto: update 生产环境能用吗？
不建议。update 只新增列不删除列，长期可能不一致。生产用 Flyway 或 Liquibase 做版本管理。但开发和教学场景下，update 非常方便。
11
RESTful API 设计（54 个接口的组织）
▼
🎯 通俗比喻

像写字楼门牌号系统。一楼（/api/chat）是对话部门，二楼（/api/knowledge）是知识部门，三楼（/api/scene）是配置部门。每层楼房间号规则统一：大门口（GET 列表）、前台（POST 新增）、会议室（PUT 修改）、后门（DELETE 删除）。知道规则就能找到任何房间。

📖 技术本质

54 个接口按模块组织在 3 个 Controller 中。路径规范：/api/chat/*、/api/knowledge/*、/api/scene/*。路径常量统一在 ApiConstants.java 中。所有接口返回统一 R<T> 响应格式，异常通过 GlobalExceptionHandler 统一处理。

💭 我的理解
"54 个接口拆分后很清晰——知识模块 5 类 × 4 CRUD ≈ 25 个，场景模块类似。关键是命名规范和路径统一，新接口往哪加、老接口在哪找，一看路径就知道。"
❓ 可能追问
Q: 有 API 文档吗？
可以接入 SpringDoc 自动生成。目前靠代码结构的清晰度——ApiConstants 管路径，前端 API 文件和后端一一对应。
Q: GET/POST/PUT/DELETE 规范？
GET 获取（幂等），POST 创建（非幂等），PUT 全量更新（幂等），DELETE 删除。消息发送用 POST+UUID 消息 ID 避免重复提交。

前后端分离架构
▼
🎯 通俗比喻

餐厅的"前厅"和"后厨"分开管理。前厅（前端）接待客人、展示菜单；后厨（后端）做菜、管库存。通过"传菜窗口"（API）沟通——前厅递点单，后厨递菜。前厅不需要知道菜怎么做，后厨不关心客人坐哪桌。

📖 技术本质

前端 Vue 3 + Vite 运行在 3100 端口，通过 Vite proxy 把 /api/* 代理到后端 10002 端口。Axios 实例统一处理 Token、错误拦截。后端 WebConfig 配置 CORS。前端 TypeScript 类型（model 目录）和后端 DTO/VO 一一对应。

💭 我的理解
"最大好处是独立开发部署。前端改 UI 不重启后端，后端改逻辑不影响前端。前端从 Vue 2 升 Vue 3 后端完全不动，只要 API 契约不变。"
❓ 可能追问
Q: 跨域怎么解决的？
开发环境用 Vite proxy 代理不存在跨域。生产环境后端 WebConfig 配置 CORS——addCorsMappings 允许前端域名跨域。
Q: 前后端数据格式怎么保持一致？
后端定义 VO/DTO，前端 model 目录定义对应 TypeScript interface，目前手动同步。项目更大可用 Swagger Codegen 自动生成前端类型。

事务管理 @Transactional
▼
🎯 通俗比喻

银行转账——从 A 扣 1000，往 B 加 1000。如果扣完钱系统崩了 B 没加上怎么办？事务保证"两步要么都成功，要么都不做"。客服系统里，"保存用户消息"和"保存 AI 回复"就像转账两步——不能只存了问题没存回答。

📖 技术本质

sendMessage() 标注 @Transactional，8 步流水线在一个事务中。步骤 1 保存用户消息和步骤 6 保存 AI 回复共享事务——中间抛出运行时异常则自动回滚。LLM 调用异常在 LlmService 里 catch 返回 null，不触发事务回滚——LLM 失败不应导致整个流程失败。

💭 我的理解
"事务边界很重要。LLM 异常在 LlmService 就 catch 掉了，返回 null 触发降级而不是回滚。如果让异常冒泡到 @Transactional 外面，用户消息也会被回滚——但用户消息本身是正确的，回滚反而不对。"
❓ 可能追问
Q: @Transactional 传播行为了解吗？
默认 REQUIRED——有事务就加入，没有就新建。REQUIRES_NEW 是独立事务。NESTED 是嵌套事务。我的场景默认 REQUIRED 够了。
Q: 事务太长有什么问题？
长时间占用连接和锁。我的方法里有 LLM 网络 IO，响应慢时事务会很长。优化：把 LLM 调用拆到事务外——先拿结果再开事务做数据库操作。目前量级不大，问题不突出。

连接池 Druid
▼
🎯 通俗比喻

数据库连接像打电话——每次都拨号、等接通、通话、挂断。一天 1000 个电话每次都拨号太慢。连接池就是一次性开 10 条电话线一直不挂断，需要时拿一条来用，用完放回去。Druid 就是"电话线管理员"，还附带"通话记录"功能（SQL 监控）。

📖 技术本质

Druid 是阿里开源数据库连接池，通过 druid-spring-boot-3-starter 集成。预先创建连接放池中，应用按需获取归还，省去 TCP 握手和数据库认证开销。额外提供 SQL 监控面板，可看每条 SQL 的执行次数、耗时、慢查询等信息。

💭 我的理解
"连接池是后端必备基础设施，选 Druid 因为国内使用广泛、文档全，SQL 监控在开发阶段特别有用——可以直接看哪些查询慢、有没有 N+1 问题。"
❓ 可能追问
Q: Druid 和 HikariCP 区别？
HikariCP 是 Spring Boot 默认连接池，微基准测试性能更快，代码更简洁。Druid 优势在监控更强，有内置 Web 面板看 SQL 详情。追求极致性能选 HikariCP，需要 SQL 监控选 Druid。

前端四栏布局的组件化设计
▼
🎯 通俗比喻

客服工作台。左边是常见问题速查手册，中间是聊天窗口（核心工作区），右上角是产品目录（随时查信息），右下角是"思考过程记录本"（AI 每步怎么决策的）。四个区域独立但通过"传纸条"（组件通信）协同工作。

📖 技术本质

index.vue 是布局容器管理四个子组件。QuestionSidebar 点击通过 emit 事件通知父组件发送消息。KnowledgeSelect 选中的商品/活动 ID 通过 props/emit 传递注入对话请求。AgentWorkArea 接收 reasoningProcess 数组渲染推理链。组件不直接通信，全部通过父组件中转——单向数据流原则。

💭 我的理解
"四栏布局重点是数据流。用户右上角选商品，ID 要一路传到后端 retrieveKnowledge() 影响检索结果。我用 props down, events up 标准模式，没用 Pinia 全局状态——数据只在这一个页面内流转，不需要全局化。"
❓ 可能追问
Q: 组件通信层级太深怎么办？
嵌套超 2-3 层 props drilling 就麻烦了。可以用 provide/inject 做依赖注入，或 Pinia store 全局状态。我只有一层嵌套，props/emit 足够。

防雷指南（求职版补充）

高频追问的从容应答
📊 高并发怎么办？
Q: 系统能支撑多少并发？QPS 大概多少？
"几个瓶颈点：① LLM 调用是最大延迟瓶颈——可以引入请求队列和限流，改成异步+SSE 推送；② 知识检索目前全表扫描——数据量大时需要加索引或接 Elasticsearch；③ 历史消息可以加 Redis 缓存——同 session 消息变化不大；④ 连接池已经用了 Druid 做连接复用，Redis+Redisson 也内置了，扩展有基础。"
⭐ 没测过就说没测过，然后从架构层面分析瓶颈，比编一个数字强一百倍。
🏭 数据库表设计为什么不用通用模型？
Q: 为什么不用一个表加 type 字段？
"考虑过通用模型——一个表加 type 字段，extra_data 存 JSON。但问题是：JSON 字段不好建索引和查询；每次都要 JSON 解析影响性能；代码层面不好做类型安全。独立表虽然 Entity 多了几个，但每张表字段清晰、查询简单、索引灵活。这是在'表的数量'和'代码质量'之间的取舍。"
📋 54 个接口怎么管理的？
Q: 这么多接口怎么组织？
"三个层面：① 路径管理——所有 API 路径定义在 ApiConstants 常量类中，避免硬编码；② 代码组织——按业务模块分 3 个 Controller，各管各的接口；③ 前端对齐——API 调用函数也按模块分文件（chat.ts / knowledge.ts / scene.ts），和后端一一对应。"
👥 你们团队几个人？
"这个项目是我独立完成的——从需求分析、架构设计到前后端开发。独立开发让我对系统每个环节都有完整理解。比如为什么做双引擎、为什么用 8 步流水线，代码里每个设计决策我都能讲清楚为什么这么做。"
⭐ 说独立完成没问题，但不要显得很轻松——要让面试官知道这有工作量。

技术亮点速查卡

面试中可以主动抛出的亮点——用一句"钩子句"勾住面试官兴趣
1. 8 步对话流水线
"一条用户消息从进入系统到生成回复，要走 8 个处理步骤，像工厂流水线一样串联。"

面试官一追问 → 展开：保存消息→LLM分析→知识检索→多轮上下文→LLM生成→卡片选择→推理链构建→响应返回。每步有明确输入输出和日志。

2. 双引擎无感降级
"LLM 挂了用户感觉不到——系统自动切到关键词规则引擎，回复质量下降但服务不中断。"

面试官一追问 → 展开：两个降级点（分析和回复各一个），通过 null 返回值做切换，全链路异常 catch 不冒泡，日志标注引擎类型。

3. 推理过程可视化
"每次对话，前端都能看到 AI 的完整推理链——6 步，每步用了什么引擎、检索到什么知识。"

面试官一追问 → 展开：6步推理链（输入解析→场景识别→意图分析→情绪判断→知识检索→生成回复），前端 AgentWorkArea.vue 组件实时渲染。

4. 知识约束的 LLM 输出
"大模型最怕幻觉。我用知识检索来约束它，让它基于真实数据回答。"

面试官一追问 → 展开：数据库检索→buildKnowledgeText()格式化→注入系统提示词→Prompt明确要求"基于知识回答"→减少幻觉。

5. 两次 LLM 调用 + 不同温度策略
"一次对话调了两次 LLM——第一次做'选择题'用低温度，第二次做'写作文'用高温度。"

面试官一追问 → 展开：analyzeUserInput() temperature=0.1 做结构化分析；generateReply() temperature=0.7 做自然语言生成。同模型、不同参数、不同效果。
