# 03 - 核心设计详解

这一节只讲当前代码真实存在的设计。项目已经按 `infra-dev-scaffolding` 的技术栈重构，后端核心不再依赖重量级框架，而是用 Go 标准库 HTTP、显式接口、PostgreSQL migration 和可替换存储来表达可靠客服 Agent。

## 核心 1：从用户消息到 Agent 回复

### 设计思路

客服 Agent 的关键不是“尽量回答”，而是“有证据才回答，没有证据就兜底，高风险就转人工”。当前链路收敛为 6 个阶段：

```text
用户发送消息
  |
  v
保存 user message
  |
  v
检索知识证据
  |
  +-- 命中证据 --> 生成 rag+rule 回复，写入 evidence_ids
  |
  +-- 无证据 ----> 返回安全兜底，创建 knowledge_gap
  |
  +-- 高风险 ----> 返回转人工话术，创建 transfer_ticket
  |
  v
更新 conversation 状态
  |
  v
返回统一 JSON envelope 给控制台
```

### 关键代码位置

| 代码 | 职责 |
|------|------|
| `internal/customer/routes.go` | 挂载客服会话 API |
| `internal/platform/store/store.go` | 内存运行时与 Agent 策略 |
| `internal/platform/store/postgres.go` | PostgreSQL 运行时与事务落库 |
| `internal/platform/httpjson` | 统一请求解析和响应封装 |
| `contracts/examples/channel-protocols.json` | 渠道协议、签名和错误码样例，控制台和演示脚本共同读取；控制台可演示成功回复和失败拒绝 |
| `contracts/channel-protocol-matrix.json` | 真实平台字段映射、幂等键、来源、限流和失败码对照 |

当前核心入口是 `Runtime.SendMessage(conversationID, content)`。业务 handler 不直接碰数据库，只依赖 `Runtime` 接口。

### 关键设计

- `userMessage` 和 `agentMessage` 都会记录，方便回看会话历史。
- `evidence` 是回复依据，命中后 Agent 只基于知识文章回答。
- `gap` 是防幻觉边界，没有证据时创建知识缺口。
- `transfer_ticket` 是人工兜底边界，遇到投诉、催办、法律、人工诉求时停止自由回答。
- PostgreSQL 版本用事务保存消息、缺口、工单和会话状态。

## 核心 2：RAG 证据优先

### 设计思路

当前 V1 没有先追求复杂向量检索，而是用可讲清楚、可验证的知识证据链路：

```text
用户问题
  -> SearchKnowledge(query)
  -> knowledge_articles
  -> evidence ids
  -> Agent reply
```

这很适合教学，因为学生可以直接看到：

- 哪些知识参与了回答
- 没有知识时系统如何处理
- 知识缺口如何变成运营任务

### 检索逻辑

`SearchKnowledge` 会从文章标题、分类、正文和标签中做匹配。内存实现和 PostgreSQL 实现都遵守同一个 `Runtime` 接口，所以前端和 handler 不需要关心数据来自哪里。

```text
query
  -> title/category/tag/token matching
  -> []KnowledgeArticle
```

命中后回复格式类似：

```text
根据知识库《7 天无理由退货》：签收后 7 天内可申请无理由退货...
```

### 可靠性边界

如果 `len(evidence) == 0`，系统不会编答案，而是：

1. 创建 `KnowledgeGap`
2. 返回安全兜底话术
3. 标记消息 `FallbackReason = NO_EVIDENCE`
4. 在运营区展示待补知识

这就是防幻觉的核心：把“不知道”产品化，而不是让模型硬答。

## 核心 3：规则兜底和转人工

### 规则模型

当前规则集中在两个核心护栏：

| 规则 | 触发条件 | 动作 |
|------|----------|------|
| `NO_EVIDENCE_FALLBACK` | 没有命中知识证据 | 安全兜底并创建知识缺口 |
| `TRANSFER_THRESHOLD` | 投诉、催办、法律风险、人工诉求 | 停止自由生成并转人工 |

规则测试入口是 `/api/ops/rules/test`，前端运营区可以直接输入用户问题看命中结果。

### 判断逻辑

`evaluateRules` 的默认结果是允许回答：

```text
action = allow_answer
riskLevel = LOW
reason = EVIDENCE_OK
```

然后按优先级处理：

1. 空输入直接拒绝测试。
2. 高风险关键词命中时返回 `TRANSFER_THRESHOLD`。
3. 无证据时返回 `NO_EVIDENCE_FALLBACK`。
4. 有证据且无风险时允许回答。

### 为什么规则不复杂化

V1 的目标是教学清晰度。规则必须能解释、能演示、能落表，而不是一开始就做成复杂规则引擎。后续可以把规则表达式外置到数据库，再逐步加入优先级、灰度、审计和版本。

## 核心 4：知识缺口闭环

### 为什么知识缺口是一等模型

可靠客服 Agent 一定会遇到无法回答的问题。真正重要的是系统如何处理这个边界。

当前知识缺口包含：

| 字段 | 说明 |
|------|------|
| `id` | 缺口 ID |
| `conversation_id` | 来源会话 |
| `question` | 用户原始问题 |
| `reason` | 缺口原因 |
| `status` | `OPEN` 或 `RESOLVED` |
| `priority` | 运营优先级 |

### 运营动作

控制台支持两类动作：

- 关闭缺口：`/api/knowledge/gaps/resolve`
- 从缺口创建文章：`/api/knowledge/gaps/create-article`

从缺口创建文章时，系统会新增 `KnowledgeArticle`，并把缺口置为已处理。这样学生能看到完整闭环：

```text
用户问未知问题
  -> Agent 不编答案
  -> 记录知识缺口
  -> 运营补知识
  -> 下一次同类问题可以命中证据
```

## 核心 5：存储接口和脚手架继承

### Runtime 接口

后端最重要的工程边界是 `Runtime`：

```go
type Runtime interface {
    ListConversations() ([]Conversation, error)
    CreateConversation(customer, channel string) (Conversation, error)
    ListMessages(conversationID string) ([]Message, error)
    SendMessage(conversationID, content string) (SendMessageResult, error)
    ChannelIntegration(channel string) (ChannelIntegration, error)
    RecordChannelInbound(receipt ChannelInboundReceipt) (bool, error)
    ReceiveChannelMessage(message ChannelInboundMessage) (SendMessageResult, error)
    ListKnowledge() ([]KnowledgeArticle, error)
    SearchKnowledge(query string) ([]KnowledgeArticle, error)
    ResolveKnowledgeGap(id string) (KnowledgeGap, error)
    CreateArticleFromGap(gapID, title, category, content string, tags []string) (KnowledgeArticle, error)
    TestRule(content string) (RuleTestResult, error)
    CompareRuleVersions(content string) (RuleComparison, error)
    SubmitRuleApproval(code, approver, riskLevel, note string, sampleIDs []string) (RuleApproval, error)
    PublishCanaryRule(code, actor, note string) (RuleReleaseEvent, error)
    RollbackRule(code, actor, note string) (RuleReleaseEvent, error)
    ResolveTransferTicket(id, assignee, note string) (TransferTicket, error)
    AssignReviewTask(id, assignee string) (ReviewTask, error)
    CompleteReviewTask(id string) (ReviewTask, error)
    SubmitAnnotation(messageID, reviewer, verdict, note string, dimensions AnnotationDimensions, tags []string) (Annotation, error)
    ExportTrainingSamples(maxScore int) ([]TrainingSample, error)
    Dashboard() (Dashboard, error)
}
```

这个接口让项目同时拥有两种运行方式：

| 实现 | 用途 |
|------|------|
| `Store` | 内存演示、单元测试、快速启动 |
| `PostgresStore` | 本地真实持久化、生产式演示 |

这正是脚手架的教学价值：底层习惯稳定，业务能力可以一步步长出来。

## 核心 6：前端控制台工作流

前端不是营销页，而是客服坐席和运营人员的工作台。

```text
apps/console/src/App.tsx
  -> dashboard metrics
  -> conversation queue
  -> message composer
  -> evidence panel
  -> knowledge gaps
  -> rule version comparison
  -> rule approval gate
  -> rule release events
  -> review task queue
  -> rule tester
  -> transfer tickets
```

关键设计：

- 用户能看到每次回复的证据。
- 运营能处理知识缺口。
- 高风险对话能进入人工工单。
- 规则可以直接测试，不需要读代码。

## 本节小结

| 核心 | 学生应该掌握 |
|------|--------------|
| 对话链路 | 消息、证据、缺口、转人工如何串起来 |
| RAG 证据 | 有证据才回答，无证据就兜底 |
| 规则护栏 | `NO_EVIDENCE_FALLBACK` 和 `TRANSFER_THRESHOLD` 的边界 |
| 运营闭环 | 知识缺口如何变成知识文章 |
| 工程结构 | `Runtime` 接口如何隔离内存和 PostgreSQL |
| 脚手架继承 | Go/React/PostgreSQL 的习惯如何承载 Agent 业务 |
