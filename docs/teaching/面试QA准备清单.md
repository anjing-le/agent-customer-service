# 客服 Agent 项目 - 面试 Q&A 准备清单

## 一、项目层面

### Q1: 介绍一下你的项目？

**A:** 我做的是一个可靠 Agent 客服系统，重点不是让 AI 什么都回答，而是让它在有知识证据时回答、没有证据时兜底、高风险问题转人工。项目基于 `infra-dev-scaffolding` 重构，前端是 React + TypeScript + Vite，后端是 Go 标准库 HTTP，数据层是 PostgreSQL + pgx + SQL migration。核心链路包括多轮会话、RAG 知识检索、规则兜底、知识缺口和人工转接。

### Q2: 为什么选择做智能客服？

**A:** 客服场景非常适合讲 Agent 工程化，因为它天然有边界：订单、退换货、发票、投诉这些问题不能靠模型编答案。这个项目用知识库约束回复，用规则处理风险，用知识缺口推动运营补数据，能体现 AI 应用从 demo 到可靠系统的关键差异。

### Q3: 项目的核心功能有哪些？

**A:** 主要有五类。第一是会话管理，支持创建会话、发送消息和维护状态。第二是知识检索，Agent 回复前会查可信知识文章。第三是规则兜底，没有证据时返回安全话术并记录缺口。第四是转人工，投诉、催办、法律风险或明确人工诉求会创建工单。第五是运营控制台，可以看指标、处理知识缺口、测试规则、关闭转人工工单。

### Q4: 整体架构是怎样的？

**A:** 前端在 `apps/console`，用 React 控制台承载客服工作流。后端有多个 Go 命令入口，课堂常用 `cmd/platform-all` 一体化启动。业务模块拆成 `internal/customer`、`internal/knowledge`、`internal/ops`，平台能力放在 `internal/platform`。数据访问通过 `Runtime` 接口隔离，内存存储用于演示和测试，`PostgresStore` 用于真实持久化。

### Q5: 为什么说它是从脚手架生长出来的？

**A:** 因为底层技术和工程习惯都继承脚手架：Go 标准库 HTTP、环境变量配置、结构化 JSON 响应、PostgreSQL migration、pgx、无 ORM、脚本化质量门禁、React 控制台。学生学习这个项目时，不需要重新理解另一套技术栈，只需要关注客服 Agent 的领域设计。

### Q6: 消息发送到回复的链路是什么？

**A:** 用户消息可以来自控制台，也可以从 `/api/channels/inbound` 这类标准渠道入口进入；微信、App、平台店铺也各有 adapter 入口，把 `openId/msgId/text`、`deviceId/messageId/body`、`buyerId/eventId/message` 归一成标准 inbound。渠道入口会读取 `ChannelIntegration`，先校验声明的来源是否在 `allowedOrigins`，再按 `rateLimitPerMinute` 做每分钟限流，然后用 active/next secret ref 对应的 env 密钥做 HMAC-SHA256 签名校验，检查 timestamp 时间窗和渠道启用状态，并按 replay 开关记录 replay key。真实渠道传入 `externalMessageId` 时，系统优先用它做重复回调对账；没有时退回签名载荷幂等。通过后，系统会把外部会话 ID 映射成内部会话。进入 `SendMessage` 后，系统会读取当前会话历史，再检索知识证据。如果命中证据，默认生成 `rag+rule` 回复；配置模型客户端后，会在证据约束下生成 `llm+rag` 回复并记录 `evidence_ids`。如果没有证据，就返回兜底话术并创建 `KnowledgeGap`；如果命中转人工关键词，就创建 `TransferTicket`。最后更新会话状态，并通过统一 JSON envelope 返回给调用方。

### Q7: RAG 检索是怎么实现的？

**A:** 当前 V1 用可解释的关键词检索。`SearchKnowledge` 会在知识文章的标题、分类、正文和标签中匹配用户问题，返回命中的 `KnowledgeArticle` 列表。命中后 Agent 只基于第一条或多条证据回答，并把证据 ID 写到消息里。这个实现简单，但教学价值高，因为证据来源和兜底条件都很清楚。

### Q8: 没有知识命中时怎么防幻觉？

**A:** 系统不会硬编答案，而是触发 `NO_EVIDENCE_FALLBACK`：返回“还没有找到可靠知识依据”的安全话术，创建 `KnowledgeGap`，并把会话状态标成知识缺口。运营人员可以在控制台关闭缺口，或者从缺口创建新的知识文章。这是把防幻觉做成产品闭环，而不是只靠一句 prompt。

### Q9: 转人工是怎么做的？

**A:** 当前规则会检测“人工、投诉、法律、催”等高风险信号。命中后 Agent 回复会明确说明已转人工，不再自由生成处理结果，同时创建 `TransferTicket`。运营区可以看到工单，并通过 `/api/ops/transfers/resolve` 关闭。工单里还有渠道、SLA、升级状态和 `events` 时间线，记录创建、处理人、备注和解决事件。不同渠道会走 `ChannelPolicy`，例如平台店铺投诉比普通 Web 会话更快升级。

### Q10: 规则兜底有哪些？

**A:** 目前核心规则有两个：`NO_EVIDENCE_FALLBACK` 处理无知识证据问题，`TRANSFER_THRESHOLD` 处理投诉、催办、法律风险和人工诉求。还有一个默认路径 `allow_answer`，表示有证据且无风险时可以回答。规则测试接口 `/api/ops/rules/test` 可以直接输入用户问题验证命中结果。

### Q11: 数据库设计有哪些表？

**A:** 当前核心表围绕可靠客服 Agent 建模：`conversations` 保存会话状态和渠道，`conversation_messages` 保存用户和 Agent 消息，`knowledge_articles` 保存可信知识，`knowledge_gaps` 保存缺口，`agent_rules` 保存规则，`transfer_tickets` 保存转人工工单，`channel_policies` 保存渠道级 SLA 和风险策略。表结构通过 SQL migration 管理，不依赖自动建表。

### Q12: 为什么不用 ORM？

**A:** 这个项目的教学重点是清楚表达业务边界。SQL migration 能直接看到有哪些表、字段和约束，pgx 调用也很显式。ORM 会隐藏一些数据行为，对教学“会话、证据、缺口、工单为什么要落表”反而不够直观。脚手架本身也偏向 SQL first 的习惯。

### Q13: 多轮会话现在做到什么程度？

**A:** 当前已经有会话和消息持久化，能按会话保存用户消息和 Agent 回复，并在控制台切换不同会话。回复生成会读取最近历史，模型客户端开启时会把最近消息纳入上下文。下一步可以继续做检索改写、会话摘要和更细的 token 控制。

### Q14: 前端控制台怎么设计？

**A:** 前端是一个坐席和运营工作台，不是展示页。它包括指标区、会话队列、渠道筛选、对话区、证据区、渠道策略、知识缺口处理、规则测试和转人工工单处理。这样学生能看到 Agent 决策结果如何被人接住，而不是只看一个聊天窗口。

### Q15: 如果要接入真正的大模型，怎么扩展？

**A:** 当前已经有可选模型客户端，通过 `ANJING_LLM_API_URL`、`ANJING_LLM_API_KEY` 和 `ANJING_LLM_MODEL` 开启。它只在命中知识证据时生成回复，模型失败会回退到 `rag+rule`。边界不变：无证据不能自由回答，高风险仍转人工，模型输出需要保留 evidence 和 fallback 信息。

### Q16: 如果要提升检索效果，怎么做？

**A:** V2 可以给 PostgreSQL 加全文检索，或者接入 embedding 向量检索。关键不是换检索技术本身，而是保持证据可追踪：每次回复要知道命中了哪些知识，知识可信等级是什么，没命中时缺口如何沉淀。

### Q17: 高并发场景怎么优化？

**A:** 首先保留当前清晰边界。数据库层可以补索引、连接池参数和分页；检索层可以做缓存和异步向量化；模型层可以做超时、限流、队列和熔断；前端回复可以改为 SSE 流式输出。高风险和无证据的规则应该尽量在模型调用前执行，减少不必要成本。

### Q18: 项目目前还有哪些不足？

**A:** 当前已经接入可选模型生成、SSE 流式输出、`Message.trace`、渠道 inbound 入口、WeChat/WeCom/App/Marketplace/Douyin/Xiaohongshu adapter、`ChannelIntegration` 运行时校验、来源白名单、active/next 密钥轮换窗口、签名时间窗、`externalMessageId` 对账、replay 防重复提交、渠道集成治理视图、渠道策略、人工工单 SLA、人工质检标注和低分复盘样本导出。但还没有向量检索、更完整的上下文压缩、更细的生产级渠道验收审计。规则表达也比较简单，后续可以做规则版本、审核流、质检任务分配和灰度。当前阶段的价值是先把可靠客服 Agent 的领域边界、工程结构和运营闭环打稳。

## 二、AI 应用层面

### Q1: 什么是 RAG？

**A:** RAG 是检索增强生成。它不是直接让模型回答，而是先从知识库检索可信资料，再让模型基于资料回答。这个项目即使 V1 还没有接入复杂模型，也已经保留了 RAG 的核心约束：回复必须绑定知识证据，没有证据就兜底。

### Q2: 什么是幻觉？怎么解决？

**A:** 幻觉是模型编造不存在的信息。解决方式不是只写“不要编造”的 prompt，而是做系统边界：知识检索、证据 ID、无证据兜底、知识缺口、人工转接和运营审核。这个项目把这些边界都做成了显式模型。

### Q3: 为什么需要规则，不能全交给模型？

**A:** 客服系统里有些事情不能让模型自由判断，比如投诉、法律风险、退款承诺和人工诉求。规则负责确定性边界，模型负责语言理解和表达。可靠 Agent 一定是模型能力和规则护栏的组合。

### Q4: 如何评估 AI 客服效果？

**A:** 可以看知识命中率、无证据兜底率、转人工率、缺口解决率、人工质检均分、低分样本数量、用户满意度和平均处理时长。当前 dashboard 已经展示会话、知识、缺口、规则、转人工、人工标注和 `QualitySummary` 质量摘要，控制台还能导出低分或待复核样本，方便运营复盘 prompt、answer、证据和评分。

工程上还可以跑 `./scripts/check-agent-regression.sh` 和 `./scripts/check-agent-quality.sh`，用固定问题集验证可答、无证据兜底、转人工、模型生成、模型失败回退、质量评分、人工标注回写和低分样本导出这些边界。

### Q5: 为什么知识缺口很重要？

**A:** 因为知识缺口代表系统真实不知道的地方。把缺口记录下来，运营就能补知识；知识补上后，下一次类似问题就能被可靠回答。这比让模型临时编一个答案更有长期价值。

### Q6: 大模型接入后最需要注意什么？

**A:** 第一是超时和失败兜底，模型不可用时系统仍要可用。第二是输出校验，不能让模型绕过证据边界。第三是成本控制，能用规则和知识直接处理的问题不要都发给模型。第四是可观测性，要记录模型输入摘要、命中证据、策略和结果。

### Q7: Prompt 应该怎么设计？

**A:** Prompt 要围绕边界写：角色是什么、只能基于哪些证据回答、无证据时如何表达、哪些风险必须转人工、输出格式是什么。好的 prompt 不是孤立文本，它要和检索、规则、日志、数据模型一起工作。

### Q8: 如果用户连续追问，系统怎么演进？

**A:** 可以把最近几轮消息用于查询改写，例如把“它能退吗”改写成“上一轮提到的商品是否支持退货”。同时保留会话摘要，避免无限堆历史。真正落地时要控制 token、延迟和隐私边界。

### Q9: 传统客服和 AI 客服有什么区别？

**A:** 传统规则客服稳定但不灵活，人工客服准确但成本高。AI 客服能理解更自然的问题，但有不确定性。可靠方案不是替代全部人工，而是让 AI 处理有证据的常见问题，把未知和高风险问题交给运营或人工。

### Q10: 这个项目最能体现能力的点是什么？

**A:** 不是用了某个模型，而是把 Agent 的可靠边界做成了工程系统：脚手架一致的技术栈、清晰的领域模型、统一 API、真实持久化、规则护栏、知识缺口和人工工单。这说明项目不是拼接口，而是在做可维护的 AI 应用。
